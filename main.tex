\textbf{Abstract.}
Time-series analysis increasingly combines predictive models with LLM systems that retrieve temporal context, call analytical tools, check intermediate results, and support later decisions. This survey explains how such systems are built from an LLM, general agent mechanisms, and capabilities designed for temporal data. We distinguish mechanisms that can be reused across time-series tasks from mechanisms tied to a particular task, while treating forecasting, anomaly detection, augmentation, question answering, and decision support as ways in which those capabilities are used. We review 139 in-scope works, connect their claims to the part of the system they change, and organize evaluation from agent execution and temporal consistency to task performance and decision support. The synthesis highlights the need for reusable temporal infrastructure, reliable tool and memory use, transparent evidence, and feedback-aware systems.
\end{tcolorbox}

\textbf{Keywords}: time series agents, LLM agents, temporal reasoning, time series foundation models, contextualized time series, tool use, memory, benchmark, harness.

\section{Introduction}

Time series analysis has long been organized around task-specific predictors: forecasting, classification, anomaly detection, imputation, segmentation, and representation learning. This model-centric paradigm has produced a mature ecosystem spanning classical statistical methods, deep neural architectures, foundation models, and LLM-enhanced temporal models \citep{zhang2024llmts,jiang2024empowering}. These systems remain important building blocks. Our distinction concerns the system layer being analyzed, rather than the age or family of the underlying predictor: many such models can become callable components inside a broader agent runtime. Most are designed to answer a bounded modeling question once the task, data split, features, context, and evaluation protocol have already been specified.

The task space is broader than forecasting. Time-series systems may be asked to forecast future values, classify sequence-level or window-level labels, detect anomalies and root causes, impute missing observations, answer questions about temporal evidence, retrieve event context, generate benchmarks, revise deployed forecasts, or support downstream decisions. These tasks share temporal constraints, but they do not require identical runtime components. A forecasting agent needs horizon-aware validation, model selection, ensembling, and revision contracts; an anomaly agent needs window localization, rule generation, and incident evidence; a classification agent needs channel-aware evidence and class exemplars; a QA agent needs faithful tool calls and answer grounding. This task heterogeneity is why a single undifferentiated time-series module is too coarse.

However, real temporal analysis rarely ends with a single model output~\cite{promptstoagents2026,chen2026tsagentsurvey,xu2026forecastagentsurvey,aion2026,timeclaw2026harness}. A practitioner must inspect data quality, verify temporal granularity, identify regime shifts, retrieve events, select tools, compare models, validate against chronological splits, explain evidence, revise forecasts under constraints, and turn predictions into operational decisions. Such a workflow requires a runtime that can plan, act, preserve temporal state, call specialized tools, validate intermediate artifacts, and revise its behavior, rather than only a stronger backbone model.

A central reason to study forecasting and related predictive tasks is that their outputs provide evidence for subsequent decisions. A forecast estimates what may happen under a stated information set; a decision must additionally determine what to do given objectives, constraints, costs, uncertainty, risk tolerance, and available actions. The decision may be to order inventory, adjust a forecast, escalate a diagnosis, change a control policy, or defer action and acquire more evidence. A Time-Series Agent closes, or explicitly supports, this loop from temporal evidence and prediction to validated action, revision, or accountable recommendation. Decision support therefore extends prediction with state, tools, verification, and feedback, while prediction remains a capability that an Agent can call, compare, and audit.

LLM agents provide a natural system abstraction for this broader workflow. In the general agent literature, the runtime around an LLM provides external computation, action schemas, tools, memory, state, execution loops, validators, observability, and permission boundaries \citep{ning2026codeharness,lee2026metaharness}. We describe LLM-based agents through the following runtime abstraction:

The LLM supplies language understanding, planning, and judgment; the general runtime supplies the interface and control surfaces that make actions executable, stateful, auditable, and revisable. Time series add a domain layer that a generic agent does not automatically provide. Temporal workflows expose recurring failure modes involving chronological admissibility, frequency and unit semantics, temporal alignment, and output auditability; related concerns such as missingness, non-stationarity, and uncertainty cut across these obligations rather than forming independent taxonomy axes. The \TSHarnessModule{} is therefore the part of the system that makes temporal objects native to the agent runtime rather than treating them as ordinary text. We further divide it into two levels: a \GeneralTSHarness{} that is useful across time-series tasks, and a \TaskSpecificHarness{} that is tied to forecasting, anomaly detection, classification, QA, imputation, benchmark generation, or another concrete task family.

A mechanism belongs to GH when its design remains useful beyond time-series applications without relying on temporal assumptions. The Harness then specializes into a Time-Series Harness Module. Within that module, a mechanism belongs to GTS when it is reusable across the relevant temporal task settings, and to TSK when its state, actions, rewards, or verification are tied to one task contract. Identifying TSK therefore requires knowing which temporal task contracts exist; task taxonomies from prior surveys provide that downstream structure.

These judgments apply to mechanisms rather than entire papers: one system can combine general memory and reflection, cross-task temporal tools, and a forecasting-specific validation loop. Changing from financial forecasting to traffic forecasting changes the application domain but preserves the forecasting task family; it therefore does not by itself establish cross-task generality.

The resulting hierarchy is the organizing structure of this survey. Time-Series Agent is the outer concept; its LLM side is independent of the nested Harness side, where General Harness contains the General Time-Series Harness Module and the latter contains Task-Specific Harness Modules.

\subsection{Position relative to existing surveys}

Existing surveys cover important subsets of the landscape. Classical and deep-learning surveys organize time-series research around forecasting, change-point detection, anomaly detection, and neural architectures \citep{aminikhanghahi2017changepoint}. Surveys on time-series foundation models, synthetic data, LLM integration, and multimodal temporal modeling summarize pretraining, adaptation, serialization, prompting, tokenization, cross-modal alignment, data generation, and evaluation \citep{liang2024foundation,liu2025synthetic,zhang2024llmts,jiang2024empowering,liu2025crossmodality,jiang2025multimodal}.

Among the closest related surveys, From Prompts to Agents and Chang et al. provide useful accounts of agentic time-series systems. From Prompts to Agents organizes systems through planning, reasoning, memory, tool use, and self-refinement \citep{promptstoagents2026}; Chang et al. describe reasoning topologies, objectives, and mechanism tags \citep{changsurvey2026}. Chen et al. organize the task-facing literature into forecasting and reasoning, augmentation and synthesis, anomaly detection and diagnosis, and decision support \citep{chen2026tsagentsurvey}. These surveys supply the prior component and task vocabularies from which our framework is built. We use Harness literature to define what an Agent runtime contains, then use time-series task structure to determine whether a temporal mechanism is cross-task or task-specific. Our contribution is the resulting hierarchical organization rather than a parallel task taxonomy.

Several system and position papers further motivate this runtime perspective. ATSF reframes forecasting as an iterative perception--planning--action--reflection--memory process rather than a static predictor \citep{atsf2026}. AION formalizes realistic time-series tasks through task files, workspaces, validation interfaces, artifacts, and layered review \citep{aion2026}. TimeClaw implements a time-series-native runtime with executable tools, episodic multimodal memory, auditable trajectories, and experience-driven capability evolution \citep{timeclaw2026harness}. Building on these systems, we organize the literature by the runtime layer to which each work contributes. We distinguish reusable temporal mechanisms from task-specific workflows and connect these mechanisms to recurring temporal design requirements.

\noindent\textit{Reading the table.} The table omits dimensions shared by all compared surveys and retains only discriminative coverage. Our survey spans the full set because it links model-side contributions, task organization, reasoning and workflow, system lifecycle, multi-task coverage, agent-process evaluation, and deployment-oriented decision utility.


The recent survey by Xu et al. organizes LLM-based forecasting and prediction agents around standalone LLMs, tool- and retrieval-augmented systems, and hybrid systems, while connecting methods to training, evaluation, applications, and risks \citep{xu2026forecastagentsurvey}. We include it as a direct competitor survey because it provides a forecasting-centered systems map and a careful account of contamination, leakage, calibration, cost, and deployment feedback. Its organizing unit is the forecasting/prediction system and its lifecycle; our organizing unit is the contribution locus of the underlying Harness. Thus its three system types are compatible with, but orthogonal to, our GH/GTS/TSK labels: a tool-augmented forecasting system may contribute components at different Harness depths, while each individual component is assigned only to its deepest applicable layer.

We re-read the broader literature through this additional contribution-locus question. Visible tools, memory, multimodality, decomposition, verification, and agent loops remain useful descriptors, but they do not resolve the locus decision under our protocol. We therefore use a seven-dimension \GeneralHarness{} comparison vocabulary synthesized from General Harness architecture, engineering, and agent-survey studies \citep{ning2026codeharness,lee2026metaharness,lin2026agenticharness,changsurvey2026,chen2026tsagentsurvey,xu2026forecastagentsurvey}. The surveyed sources use heterogeneous taxonomies; the seven dimensions are the common comparison layer we obtain by taking their recurring functional intersection. This vocabulary acts as a control layer, while the temporal obligations and the primary-locus rule provide the domain-specific coding and evaluation lens.

\subsection{Contributions}

This survey makes four contributions.

\begin{enumerate}
  \item We describe how a general LLM agent becomes a time-series agent by adding temporal data, operations, context, and validation.
  \item We separate general agent mechanisms, capabilities shared across time-series tasks, and mechanisms tied to one task, while allowing a work to contribute at several levels.
  \item We review the literature with explicit inclusion and comparison rules, and maintain a work-level record of each paper's claim, evidence, system contribution, and task setting.
  \item We connect system capabilities to evaluation, benchmarks, open-source resources, and open problems, including the transition from prediction to decision support.
\end{enumerate}

\section{What Is a Time-Series Agent?}

A Time-Series Agent is a system in which an LLM operates through a reusable runtime and time-series-specific modules.

The LLM supplies language understanding and reasoning. The General Harness supplies interaction, memory, tools, execution, control, planning, optimization, and coordination. The Time-Series Harness Module preserves temporal state, operations, context, and validation; statistical models, time-series foundation models, databases, simulators, retrieval systems, and evaluators operate as callable components within it.

The rest of the survey follows these construction layers. Section~3 isolates changes to the LLM; Section~4 describes the General Harness; Section~5 identifies the parts that become genuinely time-series-specific; Section~6 instantiates them under four task families; and Section~7 evaluates the resulting systems and the infrastructure needed to benchmark them.
\section{LLM-Side Contributions for Time-Series Agents}

The LLM is one of the three principal construction layers in a Time-Series Agent. This section records work that changes the model's ability to represent, align, understand, or reason about temporal data. The surrounding Harness is discussed in the following sections.

\subsection{Temporal representation and alignment}

These methods connect numerical sequences, time structure, and language representations. Time-LLM reprograms a frozen language model with text prototypes and a prompt prefix, while LLM4TS aligns a pretrained language model with time-series inputs for data-efficient forecasting \citep{jin2024timellm,chang2024llm4ts}. Multimodal systems extend the interface to visual or textual temporal context \citep{timevlm2025,timeomnivl2026}. Their contribution is the model-side representation and alignment that makes temporal signals available to language-model reasoning.

\subsection{Temporal instruction, interaction, and reasoning}

A second line teaches the model to discuss and reason over temporal evidence. ChatTS constructs synthetic time-series instruction data and time-series dialogue for understanding and reasoning \citep{chatts2025}. Its direct extension, Towards Time-Series Reasoning, combines a trainable temporal encoder with supervised reasoning traces for cross-domain perception and analysis \citep{chow2024tsreasoning}. These works make natural-language temporal interaction a learned model capability rather than only a prompt format.

\subsection{LLM adaptation and the model-side boundary}

LLM-side adaptation includes continued training, parameter-efficient adaptation, temporal adapters, and task-specific supervision. Foundational studies such as LLMTime establish what serialized numerical inputs can and cannot provide to a language model \citep{gruver2023llmtime,tan2024useful,merrill2024struggle}. We record the model-side change separately from Harness changes: a paper may contribute to this section and also introduce temporal tools, memory, or task contracts.

The model-side boundary matters because a stronger temporal encoder does not automatically create an Agent. ChatTS changes the learned alignment and reasoning capability; a tool-using system can then call that capability from a General Harness; and a task-specific verifier determines whether the resulting forecast, diagnosis, or recommendation satisfies its output contract. Keeping these contributions separate prevents model adaptation from being confused with runtime orchestration, while allowing a paper to receive multiple module labels when it genuinely changes multiple layers.

The seven dimensions organize the evidence below. Each subsection first states the general mechanism and then points to its use in a Time-Series Agent. A paper can contribute to several dimensions.

\subsection{Interface and Interaction}

Inference interfaces expose the model's input state and intermediate reasoning; action interfaces turn a decision into a tool call or executable operation; environment modeling represents observations, artifacts, and feedback; user interaction supports natural-language requests and review; and the state--action loop connects successive steps. The interface is therefore a protocol, not only a prompt: it declares the visible state, legal actions, return types, and failure signals that the next step can consume. TS-Agent \citep{tsagent2025} turns a natural-language question into explicit analytical operations and evidence logs. TimeART \citep{timeart2026} binds temporal analysis requests to structured tools, while TSAG \citep{tsag2026} exposes temporal questions, intermediate results, and final answers as separate states. In each case, the General Harness interface becomes the point where a time-series contract can later add horizons, windows, channels, and units.

\subsection{Memory and Context}

Memory and context mechanisms preserve information across turns, retrieve prior cases, and expose relevant evidence. Working memory holds the current trace and tool outputs; long-term memory stores reusable cases or procedures; and shared state lets several agents inspect the same artifacts. Agentic RAG for time-series analysis \citep{agenticrag2024} retrieves task-relevant examples and prompt knowledge, whereas TimeCAP \citep{timecap2025} uses contextual augmentation to connect retrieved evidence to a forecasting workflow. TIMECLAW \citep{timeclaw2026harness} stores auditable trajectories and multimodal experience, and ForecastCompass \citep{forecastcompass2026} uses adaptive memory to revise forecasting context. These mechanisms are General Harness contributions because the storage and retrieval loop is reusable; their temporal indexing and point-in-time rules are analyzed in Section~5.

\subsection{Tools and Execution}

Tools and execution expand the action space through code, statistical models, TSFMs, visualizers, retrievers, simulators, and validators. A useful tool specification contains an input schema, output schema, permission boundary, resource budget, and failure behavior. TimeSeriesScientist \citep{timeseriesscientist2025} delegates data inspection, model selection, and reporting to executable roles; TimeCopilot \citep{timecopilot2026} exposes forecasting models as selectable tools; and Argos \citep{argos2025} connects monitoring tools to rule proposal and review. AnomaMind \citep{anomamind2026} illustrates the same interface for anomaly localization and diagnosis. The General Harness contribution is the registry and execution loop; temporal semantics such as resampling, horizon alignment, and leakage checks belong to GTS.

\subsection{Control, Verification, and Feedback}

Control and verification route feedback, enforce constraints, manage retries, and check intermediate or final artifacts. The controller determines when a trace may continue, when a tool must be retried, and when an output must be rejected or escalated. FLAIRR-TS \citep{flairr2025} uses iterative refinement around a forecaster, while TSAG \citep{tsag2026} adds checks to the analytical interaction loop. VeriTime \citep{veritime2026} makes temporal validity an explicit verification target, and TraceBench \citep{tracebench2026} evaluates the submitted trajectory rather than only the final label. These examples separate a reusable critic-and-gate mechanism from the task-specific validity conditions enforced by the gate.

\subsection{Planning and Workflow}

Planning and workflow mechanisms decompose a request into data preparation, analysis, model selection, validation, reporting, and revision. They make intermediate states explicit, choose a tool sequence, record stopping conditions, and preserve the artifacts required to reproduce the result. TimeSeriesScientist \citep{timeseriesscientist2025} assigns complementary roles to curation, planning, forecasting, and reporting. TimeCAP \citep{timecap2025} connects context retrieval, augmentation, and prediction, while ClimateAgent \citep{climateagent2025} coordinates data, code, visualization, and report generation. AION \citep{aion2026} represents the workflow through task files, workspaces, artifacts, and validation interfaces, making the plan inspectable rather than implicit in the prompt.

\subsection{Optimization and Evolution}

Optimization and evolution improve prompts, tools, policies, memories, or trajectories using feedback. The update can be offline prompt or policy search, trajectory-level reflection, or a self-evolving Harness that promotes a new component after validation. TIMECLAW's explore--compare--distill loop \citep{timeclaw2026explore} turns successful trajectories into reusable capabilities. MetaCaster \citep{metacaster2026} treats the Agent as an engineer that generates and selects forecasters; CastFSR \citep{castfsr2026} revises context and forecasts through fast--slow reflection; and CRAFTER \citep{crafter2026} proposes temporal features and accepts them only after validation. The optimization mechanism is general; distribution shift and temporal promotion criteria are handled by GTS.

\subsection{Coordination and Scaling}

Coordination and scaling divide work among specialized roles, share state, and combine review or debate. Coordination may be cooperative, competitive, or hierarchical; the shared state and handoff protocol determine whether the final result is consistent and auditable. TS-Debate \citep{tsdebate2026} uses debate among specialized analysts, MAS4TS \citep{mas4ts2026} separates temporal analysis roles, and the AI-Meteorologist \citep{aimeteorologist2025} combines domain experts with a coordinating agent. FinCon \citep{fincon2024} assigns financial roles to analysts and a manager who aggregates evidence before a decision. These systems show why coordination is a Harness dimension; the temporal alignment of shared evidence is a separate GTS obligation.

\section{General Time-Series Harness}
\label{sec:general-ts-harness}

The General Time-Series Harness is the time-series specialization of the seven General Harness dimensions. We include a mechanism here only when its core representation, operation, or validator depends on temporal order, index, frequency, window, horizon, regime, availability time, or leakage control. This criterion follows the temporal contracts emphasized in recent time-series-agent surveys and reasoning taxonomies \citep{chen2026tsagentsurvey,changsurvey2026}. A generic chat loop, Python call, or reflection step remains General Harness.

The distinction is easiest to see at the contract boundary. General Harness specifies how an Agent stores state, invokes tools, coordinates roles, and verifies outputs. General Time-Series Harness specifies what a valid temporal state or operation means: which observations were available, how a window is aligned, which frequency and units apply, and how a revision is represented. TIMECLAW and AION make this boundary explicit through time-series-native execution, temporal grounding, and reliability mechanisms \citep{timeclaw2026harness,aion2026}.

\centering
\includegraphics[width=0.90\linewidth]{artifacts/paper_figures/aion_principles.png}
\caption{AION's three coupled time-series harness principles, reproduced from Fig.~2 of \citet{aion2026}. Temporal grounding, knowledge-grounded reasoning, and reliability mechanisms show why GTS is a temporal contract layered on top of a general runtime.}
\label{fig:aion-principles}
\end{figure}

\subsection{Interface and Interaction}

Time-series interfaces extend the general action schema with temporal arguments: as-of time, forecast origin, horizon, frequency, window, channel, unit, and revision. A slice action must state its interval; an aggregation must state its calendar and timezone; and a forecast must state the origin and horizon. TS-Agent \citep{tsagent2025} exposes executable temporal analysis requests, TimeART \citep{timeart2026} structures the request and result objects, and TSAG \citep{tsag2026} couples temporal questions to operations such as trend detection and correlation. These systems turn temporal meaning into an interface contract rather than leaving it implicit in a prompt.

\subsection{Memory and Context}

Temporal memory preserves time-indexed state, missingness, provenance, data vintage, event history, and revision records. The state remains queryable as it was known at a declared time, which distinguishes it from an ordinary conversation buffer. TIMECLAW \citep{timeclaw2026harness} stores execution trajectories and multimodal experience; ForecastCompass \citep{forecastcompass2026} retrieves adaptive forecasting context; and FinMem \citep{finmem2023} organizes financial evidence into layered memories. MemCast \citep{memcast2026} uses hierarchical temporal experience to guide forecast refinement. Their common GTS contribution is the temporal key attached to memory: an event or trajectory is usable only when its availability, vintage, and revision status are known.

\subsection{Tools and Execution}

Time-series tools implement temporal slicing, resampling, aggregation, decomposition, backtesting, forecasting, anomaly localization, imputation, and context alignment. Their semantics must specify intervals, horizons, time zones, units, and missing-data behavior. TimeSeriesScientist \citep{timeseriesscientist2025} and TimeCopilot \citep{timecopilot2026} expose model and analysis selection as callable operations. Argos \citep{argos2025} binds monitoring operations to a temporal metric workspace, while AnomaMind \citep{anomamind2026} connects detection, localization, diagnosis, and numerical diagnostics. The temporal tool boundary is where numerical fidelity and chronological admissibility become executable checks.

\subsection{Control, Verification, and Feedback}

Temporal control checks chronological splits, allowed-context policies, leakage, units, frequency, drift, uncertainty, and evidence completeness. A validator can reject a future-leaking retrieval, an invalid window, an inconsistent unit conversion, or an unsupported probabilistic claim before the result reaches a user. AION \citep{aion2026} exposes validation interfaces and layered review; VeriTime \citep{veritime2026} tests temporal validity conditions; and TraceBench \citep{tracebench2026} records intervention-aware trajectories for root-cause attribution. These checks define the GTS contract independently of the final task metric.

\subsection{Planning and Workflow}

Temporal workflows schedule rolling-origin evaluation, horizon-aware model selection, context retrieval by availability time, forecast revision, incident escalation, and report generation. ATSF \citep{atsf2026} makes perception, planning, action, reflection, and memory an iterative forecasting loop. AION \citep{aion2026} binds task files to temporal workspaces and validation artifacts, while ForecastCompass \citep{forecastcompass2026} combines adaptive memory with model selection and forecast revision. The GTS contribution is the temporal checkpoint carried through each planning step.

\subsection{Optimization and Evolution}

Temporal optimization uses regimes, temporal experience, shifting distributions, and revision outcomes to update prompts, tools, memories, or policies. TIMECLAW \citep{timeclaw2026explore} evolves capabilities from evaluated trajectories; MetaCaster \citep{metacaster2026} searches over generated forecasters; CastFSR \citep{castfsr2026} adapts retrieval and reflection to the current series; and CRAFTER \citep{crafter2026} validates proposed temporal features. The GTS condition is that promotion and rollback remain valid under temporal shift.

\subsection{Coordination and Scaling}

Multi-agent temporal coordination shares aligned series, event windows, provenance, and evidence identifiers across numeric, visual, textual, planning, and review roles. MAS4TS \citep{mas4ts2026} separates temporal analysis roles, FinCon \citep{fincon2024} coordinates financial analysts and a manager, and ClimateAgent \citep{climateagent2025} joins data, code, visualization, and report agents. The GTS requirement is a common temporal state: without aligned timestamps and provenance, coordination can produce internally consistent but temporally misaligned conclusions.

\subsection{Cross-dimensional temporal requirements}

The seven dimensions jointly enforce six recurring requirements:

\begin{itemize}
  \item \textbf{Temporal causality}: future observations, labels, events, or revisions do not enter an earlier state, action, retrieval, or evaluation.
  \item \textbf{Numerical fidelity}: values, scales, units, timestamps, and precision survive representation and tool boundaries.
  \item \textbf{Time-indexed state integrity}: alignment, missingness, channels, provenance, and data vintage remain available and auditable.
  \item \textbf{Temporal operation semantics}: slicing, resampling, aggregation, forecasting, localization, and metric operations have explicit interval and horizon semantics.
  \item \textbf{Temporal grounding}: external context is bound to the relevant interval, lag, horizon, availability time, provenance, and causal assumptions.
  \item \textbf{Output auditability}: analytical outputs expose a task-appropriate checker, metric, evidence trace, or review protocol, with uncertainty validation when probabilistic semantics apply.
\end{itemize}

These requirements are the cross-task design checklist; the next section instantiates them under four task contracts.
\section{Task-Specific Time-Series Harness}
\label{sec:task-specific-harness}

Task-specific Harness modules instantiate the General Time-Series Harness under a concrete output contract. We use four task families and apply the same seven-module lens within each one: interface, memory, tools, control and verification, planning, optimization, and coordination.

\subsection{Forecasting and Prediction}

Forecasting agents manage horizons, chronological splits, model selection, probabilistic outputs, revision, and deployment constraints. The interface exposes the forecast origin, horizon, frequency, and target channels; memory preserves point-in-time covariates, prior forecasts, and revisions; and tools provide model fitting, backtesting, ensembling, and reconciliation. TimeSeriesScientist \citep{timeseriesscientist2025} constructs a role-based forecasting workflow, TimeCAP \citep{timecap2025} adds contextual augmentation, and TimeCopilot \citep{timecopilot2026} selects among forecasting models as callable tools. Last-Mile Forecasting \citep{lastmile2026} focuses on decision-ready revision, HydroAgent \citep{hydroagent2026} couples hydrological simulation with warnings, and CastFlow \citep{castflow2026} iteratively refines forecasts using multi-view evidence. The TSK contract is the horizon-specific output together with leakage-controlled validation and revision rules.

\subsection{Data Augmentation and Synthesis}

Augmentation and synthesis agents generate, select, or validate temporal data and representations. BRIDGE \citep{bridge2025} conditions temporal generation on language and evaluates the generated series; MERIT \citep{merit2025} combines similar-series retrieval, augmentation, and review; and SCENARIODIFF \citep{scenariodiff2026} generates forecast-relevant scenarios from multimodal anchors. The interface declares the conditioning window, channels, sampling frequency, and intended use; memory records source series, transformations, and provenance; and verification compares temporal dependence, missingness, distributional fidelity, and downstream utility. The TSK contract is therefore the generator--validator loop, rather than generic data generation alone.

\subsection{Anomaly Detection and Diagnosis}

Anomaly agents localize events, propose or verify rules, retrieve incident evidence, diagnose causes, and support remediation. AnomaMind \citep{anomamind2026} separates coarse evidence acquisition, adaptive evidence construction, detection, and iterative refinement. ChatAD \citep{chatad2026} uses language-guided anomaly reasoning, while SAGE-AD \citep{sagead2026} and LEMAD \citep{ji2025lemad} connect detection to diagnosis and service context. Large-model-based smart agents \citep{wang2026large} use temporal evidence to interpret power-system anomalies. The TSK contract fixes monitoring windows, thresholds, root-cause labels, false-alarm budgets, alert policies, and deployment gates.

\subsection{Decision Support}

Decision-support agents connect forecasts or diagnoses to actions under costs, constraints, uncertainty, and review requirements. FinCon \citep{fincon2024} coordinates analyst evidence before portfolio decisions, TradingAgents \citep{tradingagents2024} turns market and news analysis into risk-aware trading actions, and CoLLMLight \citep{collmllight2026} uses simulation feedback for network-wide signal control. ClimateAgent \citep{climateagent2025} connects climate analysis to operational workflows, while Smart Energy Agent \citep{smartenergyagent2026} converts appliance-level anomalies into maintenance recommendations. The TSK interface represents the current state, available actions, timing, and authority; control checks risk limits and counterfactual consequences; and human review records whether the recommendation was accepted, revised, or escalated.

The complete corpus is multi-label across components: a work may contribute to several Harness dimensions and several task families, but each individual component is assigned to its deepest applicable Harness layer. The maintained ledger records both the inclusive evidence fields and the exclusive plotting labels, alongside the independent LLM-side contribution.
\section{Infrastructure and Benchmarks for Time-Series Agents}
\label{sec:evaluation}

A Time-Series Agent requires evaluation at three levels: General Harness process, time-series contract, and task outcome. Existing resources cover fragments of this contract; the benchmark gap is the absence of a widely adopted cross-task suite that evaluates them together.

\subsection{Evaluation contract}

Evaluation should report tool-call validity, trace faithfulness, memory and artifact provenance, temporal availability rules, numerical fidelity, temporal operations, evidence grounding, task metrics, cost, failures, and revision behavior. A forecast score or QA score is one task result, not a complete Agent evaluation.

The unit of evaluation should be an episode rather than a single answer. An episode records the task specification, as-of boundary, visible context, tool calls, intermediate artifacts, validator decisions, revision steps, final output, and resource use. This record makes it possible to separate a poor model prediction from a tool-selection error, a leakage error, an invalid temporal operation, or a failure to revise after feedback.

The same protocol should support controlled perturbations: hide or reveal contextual evidence, shift the forecast origin, inject missingness, change the frequency, or replace a tool with a failing implementation. These interventions expose whether a system relies on the intended temporal evidence and whether its General Harness can recover from operational failures.

\subsection{Role of QA within a Time-Series Agent benchmark}

QA resources evaluate temporal answers, evidence grounding, and selected numerical reasoning. They provide the language-facing part of evaluation; a complete Agent benchmark adds chronological validity, numerical fidelity, forecasting-horizon behavior, anomaly localization, augmentation quality, downstream decision utility, tool-call correctness, memory provenance, and validation traces.

\subsection{Infrastructure and the missing unified benchmark}

TimeClaw, AION, TimeSeriesGym, and ModernTSF provide complementary infrastructure. ModernTSF contributes an agent-ready and reproducible forecasting substrate with model and dataset catalogs, callable interfaces, evidence, budgets, artifacts, and recoverable execution \footnote{ModernTSF repository: \url{https://github.com/Diaugeia/ModernTSF}.}. We use it as an infrastructure case, not as evidence that the benchmark gap has been closed. The field still lacks a single public suite that combines a time-indexed availability policy, executable temporal tools, trace and evidence validation, and task contracts across forecasting, augmentation, anomaly diagnosis, and decision support.

A reusable benchmark stack should therefore include a time-indexed workspace, explicit availability rules, executable temporal tools, trace and evidence schemas, validators, cases from all four task families, and cost, failure, and revision logs. These requirements connect the infrastructure chapter to the open problems below.
\section{Open Problems and Focused System Analyses}

\subsection{Reusable temporal infrastructure}

Time-Series Agents need shared workspaces, temporal tool contracts, evidence schemas, validators, and reproducible execution. ModernTSF, TimeClaw, AION, and related projects show complementary pieces of this stack.

\subsection{Open problems}

\noindent\textbf{Temporal and numerical faithfulness.} Agents need typed temporal operations, unit-aware representations, chronology guards, and end-to-end fidelity checks. A correct textual explanation can still be wrong if a tool uses the wrong frequency, rounds a value, or retrieves information after the forecast origin. Future systems should therefore validate numerical and temporal invariants at every interface, not only score the final answer.

\noindent\textbf{Context retrieval and memory without leakage.} Retrieved events and episodic memories need availability-time provenance, expiry, regime awareness, and replayable audits. This problem links GTS memory to evaluation: an Agent should be able to reconstruct exactly which event, revision, or prior trajectory was visible when a decision was made.

\noindent\textbf{Interface standardization.} Shared schemas for temporal workspaces, tools, traces, and validators would make systems composable and comparable. Without a common contract, two Agents may report the same metric while using different as-of policies, window semantics, or failure handling.

\noindent\textbf{Self-evolving components.} Tool, policy, memory, and workflow updates require regression checks under temporal shift. Capability evolution should preserve previous generations when a new component fails held-out temporal checks, and should record the evidence that justified promotion.

\noindent\textbf{Decision-centric evaluation.} Future benchmarks should connect predictive or diagnostic evidence to action quality, cost, uncertainty, and accountability. Prediction is valuable because it informs action; an Agent benchmark should therefore measure whether a forecast or diagnosis changes a decision appropriately under explicit constraints, rather than treating prediction accuracy as the endpoint.

\subsection{Focused system analyses}

\noindent\textbf{ChatTS: changing the LLM side.} ChatTS starts from a limitation of ordinary language models: time-series values and temporal attributes are not natively available as a multimodal input. Its attribute selector, synthetic time-series/text generator, evolution-instruct stage, and multimodal model align numerical series with language supervision \citep{chatts2025}. In our ledger this is an LLM-side contribution with a General Time-Series Harness binding: the learned alignment is reusable across temporal questions, while the dialogue and reasoning tasks provide task-specific instantiations. The central evidence is not simply a higher answer score; it is the change in what the LLM can represent and explain, together with the synthetic-data assumptions shown in Fig.~\ref{fig:chatts-overview}.

\noindent\textbf{TimeClaw: making temporal semantics executable.} TimeClaw turns the GTS boundary into a runtime: numerical execution remains server-side, temporal tools evolve through an evaluated toolbox, and solution trajectories remain auditable and reusable \citep{timeclaw2026harness}. Its contribution is therefore broader than a forecasting model: it binds tool calls, temporal state, memory, and capability evolution to one execution contract.

\noindent\textbf{ModernTSF: infrastructure and reproducibility.} ModernTSF represents the infrastructure contribution: callable model and dataset interfaces, evidence, budgets, artifacts, and recoverable execution provide a foundation for reproducible Agent evaluation \footnote{ModernTSF repository: \url{https://github.com/Diaugeia/ModernTSF}.}. Its role in this survey is to show what must be made executable and inspectable before a benchmark can compare Agents: data and model identity, tool inputs and outputs, budgets, intermediate artifacts, and recoverable failures. It is complementary to the benchmark resources in Table~\ref{tab:benchmark-families}; it does not by itself supply a unified cross-task evaluation protocol.

\section{Conclusion}

A Time-Series Agent is built by combining an LLM, a General Harness, and a Time-Series Harness Module. The survey separates the model-side contribution from the runtime contribution, organizes the General Harness through seven shared dimensions, extracts genuinely temporal mechanisms into the General Time-Series Harness, and instantiates them under forecasting, augmentation, anomaly diagnosis, and decision support. Evaluation then follows the same construction: process, temporal contract, and task outcome. The remaining research challenge is to make these layers interoperable and to evaluate them with a unified, reproducible benchmark.
