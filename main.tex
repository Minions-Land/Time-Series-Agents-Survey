\textbf{Abstract.}
Time series research is moving from isolated prediction models toward agentic systems that inspect temporal data, retrieve context, call analytical tools, validate intermediate evidence, revise outputs, and support downstream decisions. This transition creates a conceptual gap for the community: existing surveys explain large language models for time series, time-series foundation models, or multimodal temporal reasoning, but they do not fully specify what makes an LLM-based system an agent for temporal analysis. This survey provides a component-level guide to that gap. It clarifies the operational meaning of an Agent and a Time Series Agent, identifies the runtime components that turn an LLM into a stateful, tool-using, verifiable system, and reviews what current Time Series Agents have implemented. We distinguish general-agent infrastructure, cross-task time-series Harness modules, and task-specific Harness modules for forecasting, anomaly detection, classification, QA, benchmark generation, and deployment. We further maintain a work-level component ledger so that future Time Series Agents can be compared not only by final predictive accuracy, but also by contribution locus, tool correctness, temporal faithfulness, context use, trace quality, and decision-oriented reliability.
\end{tcolorbox}

\textbf{Keywords}: time series agents, LLM agents, temporal reasoning, time series foundation models, contextualized time series, tool use, memory, benchmark.

\section{Introduction}

Time series analysis has long been organized around task-specific predictors: forecasting, classification, anomaly detection, imputation, segmentation, and representation learning. This model-centric paradigm has produced a mature ecosystem spanning classical statistical methods, deep neural architectures, foundation models, and LLM-enhanced temporal models \citep{zhang2024llmts,jiang2024empowering}. These systems are essential, but most of them are designed to answer a bounded modeling question once the task, data split, features, context, and evaluation protocol have already been specified.

The task space is broader than forecasting. Time-series systems may be asked to forecast future values, classify sequence-level or window-level labels, detect anomalies and root causes, impute missing observations, answer questions about temporal evidence, retrieve event context, generate benchmarks, revise deployed forecasts, or support downstream decisions. These tasks share temporal constraints, but they do not require identical runtime components. A forecasting agent needs horizon-aware validation, model selection, ensembling, and revision contracts; an anomaly agent needs window localization, rule generation, and incident evidence; a classification agent needs channel-aware evidence and class exemplars; a QA agent needs faithful tool calls and answer grounding. This task heterogeneity is why a single undifferentiated time-series module is too coarse.

However, real temporal analysis rarely ends with a single model output. A practitioner must inspect data quality, verify temporal granularity, identify regime shifts, retrieve events, select tools, compare models, validate against chronological splits, explain evidence, revise forecasts under constraints, and turn predictions into operational decisions. These steps require a system-level runtime, not only a stronger backbone model.

LLM agents provide a natural system abstraction for this broader workflow. In the general agent literature, the runtime around an LLM provides external computation, action schemas, tools, memory, state, execution loops, validators, observability, and permission boundaries \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness}. A concise operational reading is:

The LLM supplies language understanding, planning, and judgment; the general runtime supplies the interface and control surfaces that make actions executable, stateful, auditable, and revisable. Time series add a domain layer that a generic agent does not automatically provide. Temporal data require chronological causality, leakage control, frequency and unit semantics, temporal alignment, missingness handling, non-stationarity awareness, uncertainty treatment, and metric-verifiable numerical outputs. The \TSHarnessModule{} is therefore the part of the system that makes temporal objects native to the agent runtime rather than treating them as ordinary text. We further divide it into two levels: a \GeneralTSHarness{} that is useful across time-series tasks, and a \TaskSpecificHarness{} that is tied to forecasting, anomaly detection, classification, QA, imputation, benchmark generation, or another concrete task family.

This framing separates three kinds of contribution that are often conflated. A paper may improve the \GeneralHarness{}: planning, tool use, reflection, memory retrieval, tool synthesis, debate, control, or system optimization. It may improve the \GeneralTSHarness{}: time-indexed workspaces, typed temporal operations, context-series alignment, leakage-aware control, metric-verifiable outputs, temporal memory, or shared benchmark protocols. Or it may improve a \TaskSpecificHarness{}: forecast validation and revision, anomaly-rule synthesis, classification exemplar reasoning, TSQA tool schemas, imputation operators, or task-specific data generation. Mature Time Series Agents usually combine all three layers, but the contribution should identify which layer is novel.

\subsection{Position relative to existing surveys}

Existing surveys cover important subsets of the landscape. Classical and deep-learning surveys organize time-series research around forecasting, change-point detection, anomaly detection, and neural architectures \citep{lim2021deepts,aminikhanghahi2017changepoint,darban2024anomaly,wen2023transformers}. As larger temporal backbones emerged, surveys on time-series foundation models and synthetic data summarized pretraining, adaptation, scaling, data generation, and evaluation practices \citep{liang2024foundation,liu2025synthetic}. LLM-oriented surveys then focused on serialization, prompting, tokenization, reprogramming, cross-modal alignment, model integration, and the limits of LLMs as direct numerical forecasters \citep{zhang2024llmts,jiang2024empowering,liu2025crossmodality}. Multimodal time-series surveys further organize text, image, sensor, event, and structured temporal evidence \citep{jiang2025multimodal,liu2025crossmodality}. More recent studies move toward prompting-to-agent transitions and reasoning-oriented temporal systems, using dimensions such as decomposition and verification, ensembling, tool use, knowledge access, multimodality, agent loops, and LLM alignment regimes \citep{promptstoagents2026,changsurvey2026}.

These surveys establish useful maps, but they are not sufficient as a design basis for Time Series Agents. The agent-oriented literature can always add new labels as the field evolves--for example, from tool use and memory to retrieval, debate, workflow orchestration, self-reflection, tool synthesis, execution learning, and capability evolution. A moving list of labels is unstable as the core organizing principle. More importantly, the Harness view already places these labels inside a known agent runtime: \HarnessInterface{} covers \CodeReasoning{}, \CodeActing{}, and \CodeEnv{}; \HarnessMechanisms{} covers \Planning{}, \Memory{}, \ToolUse{}, \Control{}, and \HarnessOptimization{}; and \ScalingHarness{} covers shared artifacts, multi-agent coordination, review, and collective verification \citep{li2026harnesssurvey,ning2026codeharness}. The central question for Time Series Agent research is therefore not whether a paper can be assigned to one more component label, but where its contribution is located. It may improve the \GeneralHarness{} shared by LLM agents, the \GeneralTSHarness{} shared across temporal tasks, or a \TaskSpecificHarness{} for forecasting, anomaly detection, classification, QA, imputation, benchmark generation, or deployment. This survey is organized around that contribution-level separation.

\subsection{Contributions}

This survey makes four contributions.

\begin{enumerate}
  \item We establish an operational framing of Time Series Agents as LLM-based systems whose general runtime is extended by a time-series-domain module.
  \item We separate the design space into \GeneralHarness{}, \GeneralTSHarness{}, and \TaskSpecificHarness{} layers, clarifying whether a method contributes to agent design, cross-task temporal runtime support, or task-specific temporal workflows.
  \item We organize existing systems through a maintained component ledger and a set of aligned tables covering general-agent design, cross-task time-series modules, and task-specific modules.
  \item We outline design and evaluation principles for future systems, with emphasis on temporal faithfulness, tool correctness, process-level evaluation, reproducible infrastructure, and downstream decision support.
\end{enumerate}

\section{Agent Components and Time-series Specialization}

\subsection{From LLMs to agents}

A standalone LLM produces text conditioned on a prompt. An agent is not only a stronger prompt. It is an LLM coupled with a runtime that controls the interaction between model outputs and the external environment. Recent agent-harness literature describes this surrounding layer as tools, APIs, sandboxes, memory, validators, state representations, permission boundaries, execution loops, and feedback channels \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness}.

Drawing on the agent-harness engineering literature, general agent design can be understood through three layers \citep{li2026harnesssurvey,ning2026codeharness}:

\begin{itemize}
  \item \HarnessInterface{}: the medium through which the model reasons, acts, and represents environment state. Code-centric systems use executable, inspectable, and stateful artifacts such as programs, tool definitions, tests, repositories, simulators, and logs.
  \item \HarnessMechanisms{}: the operational layer that sustains the agent beyond a single generation step through \Planning{}, \Memory{}, \ToolUse{}, \Control{}, and \HarnessOptimization{}.
  \item \ScalingHarness{}: the multi-agent and collaborative layer built around shared artifacts, shared execution states, structured workflows, coordination, review, and collective verification.
\end{itemize}

This decomposition is domain-agnostic. It tells us what an agent runtime must provide, but not what a time-series runtime must preserve. The domain module supplies that missing specialization.

\subsection{Why time series require a Time-series Harness Module}

Time series are ordered, scale-sensitive, and context-dependent temporal objects. A \TSHarnessModule{} must protect at least six cross-task properties:

\begin{itemize}
  \item \keyterm{Temporal causality}: future observations, labels, and events must not leak into past decisions.
  \item \keyterm{Numerical fidelity}: temporal signals should not be reduced to lossy text serialization when precise operations are required.
  \item \keyterm{Time-indexed state}: timestamps, frequency, missingness, covariates, channels, units, and revision history must be explicit runtime state.
  \item \keyterm{Temporal operation semantics}: slicing, aggregation, decomposition, smoothing, forecasting, anomaly localization, event alignment, and metric computation should be typed executable actions.
  \item \keyterm{Temporal grounding of context}: textual, visual, tabular, and event context must be grounded to intervals, lags, horizons, and causal assumptions.
  \item \keyterm{Metric-verifiable outputs}: forecasts, diagnoses, and decisions must be checked by task-specific metrics, evidence traces, and leakage-aware validation.
\end{itemize}

These properties define the \GeneralTSHarness{}: the reusable temporal substrate shared by forecasting, classification, anomaly detection, QA, imputation, retrieval, benchmark generation, and decision support. A second level is task-specific. Forecasting modules introduce horizon contracts, backtesting, model-selection policies, forecast reconciliation, ensembling, and revision ledgers. Anomaly modules introduce localization, incident windows, rule synthesis, root-cause evidence, and deployment gates. Classification modules introduce channel-wise evidence, exemplar memories, label calibration, and confidence aggregation. QA modules introduce temporal question schemas, faithful tool execution, and evidence-grounded answer checking. Imputation modules introduce missingness mechanisms, mask-aware operators, and reconstruction validation. This is why Time Series Agents are not equivalent to prompting an LLM with a CSV. The \TSHarnessModule{} changes what the LLM can observe, which actions it can take, how intermediate evidence is stored, how outputs are verified, and how experience is reused.

\section{Literature Landscape}

\subsection{Temporal models as agent components}

The component-centric view does not discard model-centric time series research. Instead, it changes its role. Classical statistical models, deep forecasters, TSFMs, LLM-based time series models, and multimodal temporal models become callable temporal tools inside the \TSHarnessModule{} \citep{zeng2023dlinear,nie2023patchtst,wu2023timesnet,ansari2024chronos,das2024timesfm,rasul2023lagllama,woo2024moirai,goswami2024moment,timegpt2023,timer2024,jin2024timellm,unitime2024,test2024,urbangpt2024,chattime2025,timevlm2025,timeomni2026,timeomnivl2026}. They may provide forecasting, representation learning, sequence generation, multimodal understanding, or domain adaptation. They are not sufficient to define an agent, but they are important capabilities that an agent can select, execute, compare, and verify.

This distinction also helps interpret the debate on LLMs for time series. Prior studies show that LLMs struggle with direct numerical forecasting or zero-shot time-series reasoning when signals are serialized as text \citep{tan2024useful,merrill2024struggle}. A domain module reduces this burden by keeping temporal objects native, exposing operations through typed tools, and using the LLM for planning, context integration, and evidence synthesis.

\subsection{Contextualized and multimodal time series}

Contextualized time series connect numerical signals with external events, documents, images, domain descriptions, and natural-language questions. Existing benchmarks evaluate whether models can use textual context for forecasting, answer temporal questions, reason over multimodal evidence, handle health signals, and solve event-informed tasks \citep{contextiskey2025,timemqa2025,mtbench2025,mmtsbench2026,tsaqa2026,tsrbench2026,hearts2026,temporalbench2026}. These evaluation settings motivate two domain components: temporal grounding of external context, and leakage-aware evaluation of context-conditioned reasoning.

The resulting literature can be read through three connected strands: time-series-only analysis, agentic temporal workflows, and contextualized or multimodal temporal reasoning \citep{timeclaw2026harness}. In a Time Series Agent, these strands correspond to different parts of the \TSHarnessModule{}: contextual methods contribute evidence and retrieval interfaces, TSQA benchmarks contribute validation tasks, and multimodal temporal methods contribute cross-modal state representations.

\subsection{Agentic systems for temporal workflows}

Early Time Series Agent work makes temporal reasoning tool-grounded. TS-Agent reasons over raw time series through iterative statistical insight gathering \citep{tsagent2025}. TimeART trains tool-augmented time-series reasoning on TimeToolBench \citep{timeart2026}. TSAG evaluates financial tool selection and faithfulness \citep{tsag2026}. FETA and ZARA use multi-agent or retrieval-augmented reasoning for training-free classification and motion time-series reasoning \citep{feta2025,zara2025}. These works primarily contribute to interface design and tool-use mechanisms.

Workflow agents place temporal models inside end-to-end analysis procedures. Existing systems decompose forecasting into curation, planning, modeling, validation, reporting, retrieval, explanation, assistant interaction, and last-mile revision \citep{timeseriesscientist2025,timecap2025,timexl2025,flairr2025,nexus2026,moiraiagent2026,timecopilot2026,lastmile2026}. Similar workflow designs have also been developed for anomaly detection and diagnosis \citep{argos2025,anomamind2026}.

Multi-agent systems coordinate heterogeneous evidence or roles. TS-Debate separates numeric, visual, and textual evidence agents, while MAS4TS coordinates Analyzer, Reasoner, and Executor roles for visual time-series reasoning \citep{tsdebate2026,mas4ts2026}. These works primarily contribute to multi-agent coordination, but their value depends on a shared temporal evidence state.

\subsection{Adjacent LLM agents for data science}

Time Series Agents also inherit ideas from LLM agents for data science and machine-learning engineering. Prior work shows how agents can write code, inspect intermediate outputs, reuse cases, modify files, run experiments, and reason over machine-learning pipelines \citep{datainterpreter2025,dsagent2024,mlagentbench2024}. These systems are not time-series agents by themselves, but they define \GeneralHarness{} mechanisms--code execution, experiment management, stateful artifacts, and evaluation feedback--that can be specialized by a \GeneralTSHarness{} and then by task-specific temporal modules. In our component map, they mainly inform the general-agent layer, whereas time-series agent systems specialize those mechanisms for temporal data and concrete temporal tasks.

\subsection{Self-evolving and component-explicit systems}

Recent systems make runtime components trainable or self-extending. They formulate forecasting as sequential decision-making, compare execution trajectories using task metrics, distill successful procedures into reusable experience, fuse semantic reasoning with time-series foundation models, synthesize task-specific training data, and formalize realistic tasks through workspaces and validation interfaces \citep{castr12026,timeclaw2026explore,kairosagent2026,metacaster2026,aion2026}.

This direction is especially relevant when the system explicitly designs the \TSHarnessModule{} rather than only a task-specific prompt or workflow. A time-series-native runtime can host series in a task-local workspace, expose executable temporal tools, store episodic multimodal memory, and evolve new tools from verified trajectories, thereby connecting forecasting with contextual reasoning and domain-specific temporal analysis \citep{timeclaw2026harness}.

\section{Evaluation: From Output Metrics to Process Metrics}

Evaluating a Time Series Agent requires more than scoring the final answer. A process-level benchmark should record the task contract, allowed context, chronological boundary, tool trace, evidence chain, final artifact, and post-hoc feedback. We distinguish four evaluation layers.

\begin{enumerate}
  \item \keyterm{Model capability benchmarks}. Standard forecasting, classification, anomaly-detection, and transfer suites remain relevant for evaluating temporal model components inside an agent runtime \citep{zhang2024llmts,jiang2024empowering}.
  \item \keyterm{Contextual and multimodal reasoning benchmarks}. Context-conditioned and multimodal benchmarks evaluate whether systems can combine numerical signals with textual, visual, event, domain, or health context \citep{contextiskey2025,timemqa2025,mtbench2025,mmtsbench2026,temporalbench2026,tsrbench2026,tsaqa2026,hearts2026,tsskill2026}.
  \item \keyterm{Agent-process benchmarks}. Process-oriented benchmarks evaluate multi-turn analysis, tool selection, answer faithfulness, benchmark generation, active context retrieval, and machine-learning engineering workflows \citep{timesagemt2026,tsag2026,timeseriesgym2025,mlagentbench2024,timeseriesexamagent2026,drcik2026}.
  \item \keyterm{Deployment and live-evaluation benchmarks}. Live and deployment-oriented settings test temporal generalization, changing distributions, reproducibility, operational drift, and revision traces under business constraints \citep{impermanent2026,lastmile2026}.
\end{enumerate}

For process-level evaluation, the following metrics should be reported in addition to final accuracy or forecast error: tool-call validity, parameter correctness, evidence faithfulness, chronological leakage rate, context relevance, citation/distractor rate for retrieved context, calibration, uncertainty quality, latency, cost, memory contamination, regression under component evolution, and human-review burden.

\subsection{Open problems}

\keyterm{Interface standardization.} Current systems use different tool schemas, workspaces, trace formats, and validation contracts. A Model Context Protocol-style interface for temporal tools and workspaces could make Time Series Agents comparable and composable.

\keyterm{Numerical and temporal faithfulness.} LLMs can misread scales, ignore units, hallucinate trends, or reason over future information. Typed temporal tools, unit annotations, chronological guards, and evidence-grounded generation are required.

\keyterm{Context retrieval under distractors.} Dr-CiK shows that retrieving future-relevant context is difficult when irrelevant documents are available. Temporal grounding of retrieved context and distractor-aware retrieval should become first-class benchmark dimensions.

\keyterm{Memory without leakage.} Episodic memory can improve transfer but may contaminate evaluation, encode obsolete regimes, or retrieve superficially similar but temporally irrelevant cases. Temporal memory needs provenance, expiry, family filters, and replayable audits.

\keyterm{Self-evolving components without regression.} Recent systems suggest that tools, prompts, action-selection modules, skills, and memories can evolve \citep{timeclaw2026explore,timeclaw2026harness,metacaster2026,aion2026,castr12026,kairosagent2026}. The open challenge is to verify improvement without overfitting to benchmarks or violating temporal constraints.

\keyterm{Decision-centric evaluation.} Forecasting is only one stage. Many applications require inventory decisions, trading policies, grid control, diagnosis escalation, clinical triage, or maintenance scheduling. Time Series Agent benchmarks should evaluate downstream action quality and accountability, not only predictive error.

\section{Conclusion}

This survey argues that Time Series Agents are best understood as LLMs coupled with a \GeneralHarness{} and a \TSHarnessModule{}. The \GeneralHarness{} provides the interface, mechanisms, and scaling substrate that make an LLM into an agent. The \TSHarnessModule{} should be separated into a \GeneralTSHarness{} and a set of \TaskSpecificHarness{} components. The cross-task layer supplies temporal workspaces, typed operations, temporal grounding of context, leakage-aware validation, temporal memory, and domain tools. The task-specific layer supplies the concrete forecasting, anomaly, classification, QA, benchmark-generation, imputation, or deployment workflows required by applications.

This framing absorbs previous model-centric work rather than replacing it. Classical models, deep forecasters, TSFMs, LLM-based time-series models, multimodal temporal models, and statistical procedures all become callable components inside the \TSHarnessModule{}. The frontier is therefore shifting from standalone forecasting models to executable, verifiable, stateful, and adaptive temporal analysis systems. Future work should make its contribution locus explicit: whether it improves the \GeneralHarness{}, the \GeneralTSHarness{}, or a \TaskSpecificHarness{} for a concrete time-series task.
