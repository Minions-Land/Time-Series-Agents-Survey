\textbf{Abstract.}
Time-series analysis increasingly combines predictive models with LLM systems that retrieve temporal context, call analytical tools, check intermediate results, and support later decisions. This survey explains how such systems are built from an LLM, general agent mechanisms, and capabilities designed for temporal data. We organize mechanisms by their reuse across time-series tasks and by the task contracts that bind them to forecasting and reasoning, augmentation and synthesis, anomaly detection and diagnosis, and decision support. We review 130 in-scope records, connect their claims to the system components they change, and organize evaluation from agent execution and temporal consistency to task performance and decision support. The synthesis highlights the need for reusable temporal infrastructure, reliable tool and memory use, transparent evidence, and feedback-aware systems.
\end{tcolorbox}

\textbf{Keywords}: time series agents, LLM agents, temporal reasoning, time series foundation models, contextualized time series, tool use, memory, benchmark, harness.

\section{Introduction}

Time series analysis has long been organized around task-specific predictors: forecasting, classification, anomaly detection, imputation, segmentation, and representation learning. This model-centric paradigm has produced a mature ecosystem spanning classical statistical methods, deep neural architectures, foundation models, and LLM-enhanced temporal models \citep{zhang2024llmts,jiang2024empowering}. These models become callable components inside a broader agent runtime. We analyze the system layer that turns a predictor into an executable, stateful workflow with specified data, context, evaluation, and revision.

The task space is broader than forecasting. Time-series systems may be asked to forecast future values, classify sequence-level or window-level labels, detect anomalies and root causes, impute missing observations, answer questions about temporal evidence, retrieve event context, generate benchmarks, revise deployed forecasts, or support downstream decisions. These tasks share temporal constraints and require distinct runtime components. A forecasting agent needs horizon-aware validation, model selection, ensembling, and revision contracts; an anomaly agent needs window localization, rule generation, and incident evidence; a classification agent needs channel-aware evidence and class exemplars; a QA agent needs faithful tool calls and answer grounding. Task heterogeneity calls for a structured time-series harness.

Real temporal analysis extends beyond a single model output~\cite{promptstoagents2026,chen2026tsagentsurvey,xu2026forecastagentsurvey,aion2026,timeclaw2026harness}. A practitioner inspects data quality, verifies temporal granularity, identifies regime shifts, retrieves events, selects tools, compares models, validates chronological splits, explains evidence, revises forecasts under constraints, and turns predictions into operational decisions. This workflow requires a runtime that plans, acts, preserves temporal state, calls specialized tools, validates intermediate artifacts, and revises its behavior.

A central reason to study forecasting and related predictive tasks is that their outputs provide evidence for subsequent decisions. A forecast estimates what may happen under a stated information set; a decision must additionally determine what to do given objectives, constraints, costs, uncertainty, risk tolerance, and available actions. The decision may be to order inventory, adjust a forecast, escalate a diagnosis, change a control policy, or defer action and acquire more evidence. A Time-Series Agent connects temporal evidence and prediction to validated action, revision, or accountable recommendation. Decision support extends prediction with state, tools, verification, and feedback; prediction remains a capability that an Agent can call, compare, and audit.

LLM agents provide a natural system abstraction for this broader workflow. In the general agent literature, the runtime around an LLM provides external computation, action schemas, tools, memory, state, execution loops, validators, observability, and permission boundaries \citep{ning2026codeharness,lee2026metaharness}. We describe LLM-based agents through the following runtime abstraction:

The LLM supplies language understanding, planning, and judgment; the general runtime supplies the interface and control surfaces that make actions executable, stateful, auditable, and revisable. Time series add a domain layer with chronological admissibility, frequency and unit semantics, temporal alignment, missingness, non-stationarity, uncertainty, and output auditability. The \TSHarnessModule{} makes these temporal objects native to the agent runtime. It has two levels: a \GeneralTSHarness{} reusable across time-series tasks and a \TaskSpecificHarness{} tied to forecasting, anomaly detection, classification, QA, imputation, benchmark generation, or another concrete task family.

A mechanism belongs to GH when it remains useful beyond time-series applications and has no temporal assumptions. Within the Time-Series Harness Module, GTS denotes mechanisms reusable across temporal task settings, whereas TSK denotes mechanisms whose state, actions, rewards, or verification follow one task contract. Prior task taxonomies define these downstream contracts.

The labels describe mechanisms. A single system can combine general memory and reflection, cross-task temporal tools, and a forecasting-specific validation loop; the temporal layer then follows the forecasting contract across financial and traffic domains.

The resulting hierarchy is the organizing structure of this survey. Time-Series Agent is the outer concept; its LLM side is independent of the nested Harness side, where General Harness contains the General Time-Series Harness Module and the latter contains Task-Specific Harness Modules.

The survey maintains a module-level evidence ledger described in Appendix~\ref{app:full-ledger}. The ledger records claims, source locators, contribution modules, task contracts, evaluation evidence, and review status; its fields support the comparison tables and module-level plots used throughout the paper.

\subsection{Position relative to existing surveys}

Existing surveys cover important subsets of the landscape. Task-oriented surveys discuss forecasting, change-point detection, anomaly detection, and deep architectures from their respective methodological perspectives \citep{aminikhanghahi2017changepoint,lim2021deepts,darban2024anomaly}. Surveys on time-series foundation models, synthetic data, LLM integration, and multimodal temporal modeling summarize pretraining, adaptation, serialization, prompting, tokenization, cross-modal alignment, data generation, and evaluation \citep{liang2024foundation,liu2025synthetic,zhang2024llmts,jiang2024empowering,liu2025crossmodality,jiang2025multimodal}.

Among the closest related surveys, \textit{From Prompts to Agents: A Comprehensive Survey of LLM-Driven Time Series Analysis} \citep{promptstoagents2026} separates representation, model adaptation, workflow autonomy, and analytical tasks; its workflow-autonomy axis further distinguishes predictor, augmenter, orchestrator, and multi-agent-collaboration levels, while the survey also discusses perception, planning, tool use, memory, and reflection. \textit{A Survey of Reasoning and Agentic Systems in Time Series with Large Language Models} \citep{changsurvey2026} describes reasoning topologies, objectives, and mechanism tags. \textit{LLM Agents for Time-Series: A Survey} \citep{chen2026tsagentsurvey} organizes the task-facing literature into forecasting and reasoning, augmentation and synthesis, anomaly detection and diagnosis, and decision support. These surveys supply the component and task vocabularies from which our framework is built. Harness literature defines the Agent runtime; time-series task structure determines whether a temporal mechanism is cross-task or task-specific. Our contribution is the resulting hierarchical organization.

Several system and position papers motivate this runtime perspective. ATSF frames forecasting as an iterative perception--planning--action--reflection--memory process \citep{atsf2026}. AION formalizes time-series tasks through task files, workspaces, validation interfaces, artifacts, and layered review \citep{aion2026}. TimeClaw implements a time-series-native runtime with executable tools, episodic multimodal memory, auditable trajectories, and experience-driven capability evolution \citep{timeclaw2026harness}. We organize these systems by the runtime layer each work changes and connect reusable temporal mechanisms to task-specific workflows and temporal design requirements.

\subsection{Contributions}

This survey makes four contributions.

\begin{enumerate}
  \item We describe how a general LLM agent becomes a time-series agent by adding temporal data, operations, context, and validation.
  \item We separate general agent mechanisms, capabilities shared across time-series tasks, and mechanisms tied to one task, with multi-module contributions recorded at their respective levels.
  \item We review the literature with explicit inclusion and comparison rules, and release a module-level ledger that records each paper's claim, evidence locator, contribution layer, task contract, and review status in a machine-readable form.
  \item We connect system capabilities to evaluation, benchmarks, open-source resources, and open problems, including the transition from prediction to decision support.
  \item We show how the module-level ledger turns the survey into an extensible research map: the same records that support classification also expose missing temporal contracts, evaluation gaps, and future research directions.
\end{enumerate}

\section{What Is a Time-Series Agent?}

A Time-Series Agent is a system in which an LLM operates through a reusable runtime and time-series-specific modules.

The LLM supplies language understanding and reasoning. The General Harness supplies interaction, memory, tools, execution, control, planning, optimization, and coordination. The Time-Series Harness Module preserves temporal state, operations, context, and validation; statistical models, time-series foundation models, databases, simulators, retrieval systems, and evaluators operate as callable components within it.

At an abstract level, the runtime can be written as
\begin{equation}
  a_t = \pi_\theta(s_t), \qquad
  s_{t+1} = \mathcal{H}(s_t,a_t,o_{t+1}),
  \label{eq:agent-loop}
\end{equation}
where $s_t$ is the visible state, $a_t$ is a tool or environment action, $o_{t+1}$ is the returned observation, and $\mathcal{H}$ is the Harness transition. Time-Series Harness Modules add temporal type information to each state, action, and observation.

\section{LLM-Side Contributions for Time-Series Agents}

The LLM is one of the three principal construction layers in a Time-Series Agent. This section records work that changes the model's ability to represent, align, understand, or reason about temporal data. The surrounding Harness is discussed in the following sections.

\subsection{Temporal representation and alignment}

These methods change how an LLM receives temporal values. Time-LLM reprograms a frozen language model with text prototypes and a Prompt-as-Prefix context, while LLM4TS aligns a pretrained language model with time-series inputs for data-efficient forecasting \citep{jin2024timellm,chang2024llm4ts}. Multimodal systems extend the same model-side boundary to visual or textual temporal context \citep{timevlm2025,timeomnivl2026}. Conversational Time Series Foundation Models place the LLM in the role of an ensemble judge: the model interprets temporal evidence, assigns weights to foundation forecasters, and explains the resulting forecast in dialogue \citep{conversationaltsfm2025}. STRIDE instead injects distilled reasoning into a continuous TSFM representation, coupling language-side reasoning with numerical forecasting \citep{stride2026}.

Time-LLM makes the input and output contracts explicit: for a multivariate series $X\in\mathbb{R}^{N\times T}$, the model produces a horizon of predictions $\widehat{Y}\in\mathbb{R}^{N\times H}$ and is trained with
\begin{equation}
  \mathcal{L}_{\mathrm{MSE}}=\frac{1}{H}\sum_{h=1}^{H}\left\|\widehat{Y}_{h}-Y_{h}\right\|_{F}^{2}.
  \label{eq:timellm-objective}
\end{equation}
The method first transforms the series into the language-model interface, applies a frozen LLM with Prompt-as-Prefix context, and projects the hidden states back to the forecast space \citep{jin2024timellm}. This objective captures the model-side contribution: temporal representation is aligned with the forecast space and trained under an explicit prediction loss.

\subsection{Temporal instruction, interaction, and reasoning}

A second line teaches the model to discuss and reason over temporal evidence. ChatTS constructs synthetic time-series instruction data and time-series dialogue for understanding and reasoning \citep{chatts2025}. Its direct extension, Towards Time-Series Reasoning, combines a trainable temporal encoder with supervised reasoning traces for cross-domain perception and analysis \citep{chow2024tsreasoning}. These works make natural-language temporal interaction a learned model capability. The same model-side direction appears in open-ended forecasting: OpenForecaster trains reasoning models on automatically curated future-event questions with retrieval and reinforcement learning, while AURA-4B studies tool-use post-training and PPO in a chronological stock-price sandbox \citep{openforecaster2026,auraforecaster2026}. ChatTS also preserves numerical meaning during normalization by exposing the scale and offset in the text prompt. For a series value $x_t$, its value-preserved normalization can be written as
\begin{equation}
  x_t^{\mathrm{norm}}=\frac{x_t-x_{\min}}{x_{\max}-x_{\min}},\qquad
  x_t=(x_{\max}-x_{\min})x_t^{\mathrm{norm}}+x_{\min},
  \label{eq:chatts-value-preserved}
\end{equation}
so the LLM receives normalized patches together with the parameters required to recover the original numerical scale \citep{chatts2025}. For instruction records $(x_i,q_i,r_i)$, the model-side training objective is
\begin{equation}
  \mathcal{L}_{\mathrm{dialog}}(\theta)=-\sum_{i=1}^{N}\log p_{\theta}(r_i\mid x_i,q_i).
  \label{eq:llm-dialogue-objective}
\end{equation}
ChatTS instantiates this objective with synthetic temporal attributes, instruction data, and dialogue responses \citep{chatts2025}.

The module ledger places learned data and reasoning under the LLM layer. Tool, memory, and validation contributions from the same work receive their own Harness entries, keeping multi-layer contributions visible.

\subsection{LLM adaptation and the model-side boundary}

LLM-side adaptation includes continued training, parameter-efficient adaptation, temporal adapters, and task-specific supervision. Foundational studies such as LLMTime establish the capabilities and limits of serialized numerical inputs for language models \citep{gruver2023llmtime,tan2024useful,merrill2024struggle}. Adaptation methods update a temporal interface or a parameter-efficient module while preserving the base model:
\begin{equation}
  \theta_{\mathrm{adapt}}=\theta_{0}+\Delta_{\phi},\qquad
  \Delta_{\phi}^{\star}=\arg\min_{\Delta_{\phi}}\mathcal{L}_{\mathrm{TS}}(\theta_{0}+\Delta_{\phi}).
  \label{eq:llm-adaptation}
\end{equation}
We record model-side changes alongside any temporal tools, memory, or task contracts introduced by the same paper.

A stronger temporal encoder supplies the learned alignment and reasoning capability; a General Harness makes it callable; and a task-specific verifier checks the resulting forecast, diagnosis, or recommendation against its output contract. The module ledger records these changes as separate entries when a paper contributes to multiple layers.
\section{General Harness}
\label{sec:general-harness}

The General Harness is the reusable runtime around the LLM. The reviewed Time-Series Agent corpus instantiates this runtime, while General Agent surveys provide the vocabulary and comparative basis for the seven dimensions \citep{ning2026codeharness,lee2026metaharness,lin2026agenticharness,changsurvey2026,chen2026tsagentsurvey,xu2026forecastagentsurvey}. Agent Cybernetics gives a systems-level account of reliability, lifelong operation, and self-improvement for tool loops, memory, harnesses, and reflection, which motivates the runtime dimensions used here \citep{agentcybernetics2026}.

The seven dimensions organize the evidence below. Each subsection first states the general mechanism and then points to its use in a Time-Series Agent. A paper can contribute to several dimensions.

\subsection{Interface and Interaction}

Inference interfaces expose the model's input state and intermediate reasoning; action interfaces turn a decision into a tool call or executable operation; environment modeling represents observations, artifacts, and feedback; user interaction supports natural-language requests and review; and the state--action loop connects successive steps. The interface is a protocol that declares the visible state, legal actions, return types, and failure signals consumed by the next step. TS-Agent \citep{tsagent2025} turns a natural-language question into explicit analytical operations and evidence logs. TimeART \citep{timeart2026} binds temporal analysis requests to structured tools, while TSAG \citep{tsag2026} exposes temporal questions, intermediate results, and final answers as separate states. In each case, the General Harness interface becomes the point where a time-series contract can later add horizons, windows, channels, and units. A general tool call carries the name, arguments, permissions, and resource budget needed to execute one step:
\begin{equation}
  \omega_k=(n_k,\operatorname{args}_k,\operatorname{perm}_k,b_k),\qquad
  o_{k+1}=\operatorname{Exec}(\omega_k,s_k),\qquad
  s_{k+1}=\mathcal{H}(s_k,\omega_k,o_{k+1}).
  \label{eq:gh-interface}
\end{equation}
TS-Agent, TimeART, and TSAG instantiate this boundary with analytical operations, structured intermediate states, and returned evidence.

\subsection{Memory and Context}

Memory and context mechanisms preserve information across turns, retrieve prior cases, and expose relevant evidence. Working memory holds the current trace and tool outputs; long-term memory stores reusable cases or procedures; and shared state lets several agents inspect the same artifacts. Agentic RAG for time-series analysis \citep{agenticrag2024} retrieves task-relevant examples and prompt knowledge, whereas TimeCAP \citep{timecap2025} uses contextual augmentation to connect retrieved evidence to a forecasting workflow. TIMECLAW \citep{timeclaw2026harness} stores auditable trajectories and multimodal experience, and ForecastCompass \citep{forecastcompass2026} uses adaptive memory to revise forecasting context. These mechanisms are General Harness contributions because the storage and retrieval loop is reusable; their temporal indexing and point-in-time rules are analyzed in Section~5. TimeCAP makes the dual-agent interface explicit: a contextualizer first maps the series to a textual summary and a predictor then conditions on that summary,
\begin{equation}
  s_x=A_C(x)=M_{\theta}\!\left(p_C(x)\right),\qquad
  \widehat{y}_{\mathrm{LLM}}=A_P(s_x)=M_{\theta}\!\left(p_P(s_x)\right).
  \label{eq:timecap-dual-agent}
\end{equation}
The equation is the method-level contribution: memory is not only a buffer, but a contextualizer--predictor handoff that changes the information supplied to the forecasting agent \citep{timecap2025}. At step $k$, the general memory interface retrieves evidence for the current query, merges it with the working state, and writes the resulting trace back for later reuse:
\begin{equation}
  m_k=R_{\psi}(\mathcal{M}_k,q_k), \qquad
  s_k^{+}=s_k\oplus m_k,\qquad
  \mathcal{M}_{k+1}=\operatorname{Write}(\mathcal{M}_k,\rho_k).
  \label{eq:gh-memory}
\end{equation}
Here $R_{\psi}$ covers retrieval and context selection, while $\operatorname{Write}$ covers episodic storage and experience promotion used by TIMECLAW and ForecastCompass.

\subsection{Tools and Execution}

Tools and execution expand the action space through code, statistical models, TSFMs, visualizers, retrievers, simulators, and validators. A useful tool specification contains an input schema, output schema, permission boundary, resource budget, and failure behavior. TimeSeriesScientist \citep{timeseriesscientist2025} delegates data inspection, model selection, and reporting to executable roles; TimeCopilot \citep{timecopilot2025} exposes forecasting models as selectable tools; and Argos \citep{argos2025} connects monitoring tools to rule proposal and review. AnomaMind \citep{anomamind2026} illustrates the same interface for anomaly localization and diagnosis. The General Harness contribution is the registry and execution loop; temporal semantics such as resampling, horizon alignment, and leakage checks belong to GTS. TimeSeriesScientist's Curator is a concrete tool-using module: it emits statistics, missingness and outlier information, and a preprocessing policy, then applies that policy to the input series,
\begin{equation}
  Q=A_f(D)=(S,M,O,\pi),\qquad
  \widetilde{D}=\phi_{\pi}(D),
  \label{eq:tsci-curator}
\end{equation}
where $S=(\mu,\sigma,x_{\min},x_{\max},\tau_{\mathrm{trend}})$ and $\pi$ contains the selected missing-value and outlier operations \citep{timeseriesscientist2025}. The registry therefore exposes not only a generic ``run'' action but also a data-aware diagnostic tool.
The Planner stage then evaluates the candidate model pool rather than committing to one forecaster in advance. For each candidate $m_i$ with configuration $\theta_i$, TSci selects
\begin{equation}
  \theta_i^{\star}=\arg\min_{\theta_i\in\mathcal{C}_i}
  \operatorname{MAPE}_{\mathrm{val}}\!\left(m_i(\theta_i)\right),\qquad
  \operatorname{MAPE}_{\mathrm{val}}(m_i(\theta_i))=
  \frac{100\%}{|\widetilde{D}_{\mathrm{val}}|}
  \sum_{t\in\widetilde{D}_{\mathrm{val}}}
  \left|\frac{x_t-\widehat{x}^{(i,\theta_i)}_t}{x_t}\right|.
  \label{eq:tsci-planner}
\end{equation}
The equation links tool execution to the forecasting contract: the LLM narrows the hypothesis space, while validation metrics select the configuration \citep{timeseriesscientist2025}. Let $\mathcal{T}$ denote the registered tools. The execution interface selects a legal tool call and returns a typed observation:
\begin{equation}
  \omega_k=\pi_{\theta}(s_k,\mathcal{T}),\qquad
  o_{k+1}=\operatorname{Exec}_{n_k}(\operatorname{args}_k),\qquad
  s_{k+1}=\operatorname{Update}(s_k,\omega_k,o_{k+1}).
  \label{eq:gh-tools}
\end{equation}
The registry supplies the name, argument schema, permission boundary, output type, and resource budget for each callable component.

\subsection{Control, Verification, and Feedback}

Control and verification route feedback, enforce constraints, manage retries, and check intermediate or final artifacts. The controller determines when a trace may continue, when a tool must be retried, and when an output must be rejected or escalated. FLAIRR-TS \citep{flairr2025} uses iterative refinement around a forecaster, while TSAG \citep{tsag2026} adds checks to the analytical interaction loop. VeriTime \citep{veritime2026} makes temporal validity an explicit verification target, and TraceBench \citep{tracebench2026} evaluates the submitted trajectory alongside the final label. FLAIRR-TS gives this controller a concrete test-time loop: retrieve analogous segments, augment the prompt, forecast, measure MAE, and let a stateful refiner propose the next prompt,
\begin{equation}
\begin{aligned}
  S_{\mathrm{retr}}^{(k)}&=\operatorname{RetrieveSegments}(X_{\mathrm{HistDB}},X_{\mathrm{Ctx}},M),\\
  C_{\mathrm{aug}}^{(k)}&=\operatorname{AugmentContext}(X_{\mathrm{Ctx}},S_{\mathrm{retr}}^{(k)}),\\
  \widehat{X}^{(k)}&=F_{\mathrm{LLM}}(P_{\mathrm{curr}}^{(k)},C_{\mathrm{aug}}^{(k)},H),\\
  \operatorname{mae}^{(k)}&=\operatorname{MAE}(\widehat{X}^{(k)},X_{t:t+H}),\\
  (P_{\mathrm{next}}^{(k)},d^{(k)})&=R_{\mathrm{LLM}}\!\left(\{(P^{(i)},\operatorname{mae}^{(i)})\}_{i<k},P_{\mathrm{curr}}^{(k)},\tau_{\mathrm{stop}}\right).
\end{aligned}
\label{eq:flairr-loop}
\end{equation}
The source algorithm returns the best prompt when the stopping signal is absent and terminates early when the improvement criterion is met \citep{flairr2025}. For a trajectory $\rho_{1:k}$ and result $r_k$, the generic controller opens the next step only when the process and output checks pass:
\begin{equation}
  g_k=\mathbb{1}\!\left[\mathcal{V}_{\mathrm{proc}}(\rho_{1:k})=1\;\wedge\;\mathcal{V}_{\mathrm{out}}(r_k)=1\right],
  \qquad
  \operatorname{Next}_k=\begin{cases}
    \operatorname{stop}(r_k), & g_k=1,\\
    \operatorname{retry/escalate}(\rho_{1:k}), & g_k=0.
  \end{cases}
  \label{eq:gh-control}
\end{equation}
The same gate supports iterative refinement in FLAIRR-TS, interaction checks in TSAG, and trajectory-level assessment in TraceBench.

\subsection{Planning and Workflow}

Planning and workflow mechanisms decompose a request into data preparation, analysis, model selection, validation, reporting, and revision. They make intermediate states explicit, choose a tool sequence, record stopping conditions, and preserve the artifacts required to reproduce the result. TimeSeriesScientist \citep{timeseriesscientist2025} assigns complementary roles to curation, planning, forecasting, and reporting. TimeCAP \citep{timecap2025} connects context retrieval, augmentation, and prediction, while ClimateAgent \citep{climateagent2025} coordinates data, code, visualization, and report generation. AION \citep{aion2026} represents the workflow through task files, workspaces, artifacts, and validation interfaces, making the plan inspectable and explicit. For a request $q$, planning chooses a valid sequence of operations from the available workflow space:
\begin{equation}
  \rho^{\star}=\arg\max_{\rho\in\mathcal{R}(q)}
  \left[\operatorname{Utility}(\rho)-\lambda\operatorname{Cost}(\rho)\right]
  \qquad \text{s.t.}\qquad \operatorname{Valid}(\rho)=1.
  \label{eq:gh-planning}
\end{equation}
The workflow records the selected operations, intermediate artifacts, stopping condition, and validation points.

\subsection{Optimization and Evolution}

Optimization and evolution improve prompts, tools, policies, memories, or trajectories using feedback. The update can be offline prompt or policy search, trajectory-level reflection, or a self-evolving Harness that promotes a new component after validation. TIMECLAW's explore--compare--distill loop \citep{timeclaw2026explore} turns successful trajectories into reusable capabilities. MetaCaster \citep{metacaster2026} treats the Agent as an engineer that generates and selects forecasters; CastFSR \citep{castfsr2026} revises context and forecasts through fast--slow reflection; and CRAFTER \citep{crafter2026} proposes temporal features and accepts them only after validation. MetaCaster writes the optimization target at the level of the downstream forecaster. Given a trainable Harness $\theta$, it minimizes the gap between authentic-data and generated-data forecasters,
\begin{equation}
  \theta^{\star}=\arg\min_{\theta}\;\mathbb{E}_{m,l}\,\delta\!\left(\omega(f_l^m),\omega(\bar f_l^m)\right),\qquad
  \bar D^m=\operatorname{MGAgent}(D_{\mathrm{sup}}^m,C^m),
  \label{eq:metacaster-objective}
\end{equation}
and uses the hinge-style comparison
\begin{equation}
  \delta\!\left(\omega(f_l^m),\omega(\bar f_l^m)\right)=
  \max\!\left\{\frac{\omega(\bar f_l^m)-\omega(f_l^m)}{\omega(f_l^m)},0\right\}
  \label{eq:metacaster-hinge}
\end{equation}
to penalize generated training data that produces a worse lightweight forecaster \citep{metacaster2026}. The generic evolution loop updates a Harness component from evaluated trajectories:
\begin{equation}
  \theta_{j+1}=\operatorname{Update}\!\left(\theta_j,\mathcal{D}_j\right),\qquad
  \mathcal{D}_j=\left\{(\rho_i,\operatorname{Score}(\rho_i))\right\}_{i=1}^{j}.
  \label{eq:gh-evolution}
\end{equation}
TIMECLAW promotes successful trajectories, MetaCaster searches over generated forecasters, and CastFSR updates context and forecasts through reflection.

\subsection{Coordination and Scaling}

Coordination and scaling divide work among specialized roles, share state, and combine review or debate. Coordination may be cooperative, competitive, or hierarchical; the shared state and handoff protocol determine whether the final result is consistent and auditable. TS-Debate \citep{multimodaldebate2026} uses debate among specialized analysts, MAS4TS \citep{mas4ts2026} separates temporal analysis roles, and the AI-Meteorologist \citep{aimeteorologist2025} combines domain experts with a coordinating agent. FinCon \citep{fincon2024} assigns financial roles to analysts and a manager who aggregates evidence before a decision. These systems show why coordination is a Harness dimension; the temporal alignment of shared evidence is a separate GTS obligation. With role states $s_k^{(1)},\ldots,s_k^{(J)}$, coordination aggregates role outputs before the next shared action:
\begin{equation}
  m_k^{\mathrm{shared}}=\operatorname{Aggregate}\!\left(\{m_k^{(j)}\}_{j=1}^{J}\right),\qquad
  a_k=\pi_{\theta}\left(s_k^{(1:J)},m_k^{\mathrm{shared}}\right).
  \label{eq:gh-coordination}
\end{equation}
The shared message and handoff protocol are the runtime objects used by debate, delegation, and manager--analyst systems.

\section{General Time-Series Harness}
\label{sec:general-ts-harness}

The General Time-Series Harness specializes the seven General Harness dimensions through temporal order, index, frequency, window, horizon, regime, availability time, and leakage control. This criterion follows the temporal contracts emphasized in recent time-series-agent surveys and reasoning taxonomies \citep{chen2026tsagentsurvey,changsurvey2026}; generic chat loops, Python calls, and reflection steps remain General Harness.

The contract boundary makes the distinction explicit. General Harness specifies how an Agent stores state, invokes tools, coordinates roles, and verifies outputs. General Time-Series Harness specifies what a valid temporal state or operation means: which observations were available, how a window is aligned, which frequency and units apply, and how a revision is represented. TIMECLAW and AION make this boundary explicit through time-series-native execution, temporal grounding, and reliability mechanisms \citep{timeclaw2026harness,aion2026}.

For a temporal state at decision time $\tau$, the admissible information can be represented as
\begin{equation}
  \mathcal{I}_{\tau} = \{(x_i,t_i,v_i): t_i \leq \tau,\; v_i \leq \tau\},
  \label{eq:temporal-availability}
\end{equation}
where $t_i$ is the event time and $v_i$ is the time at which the value became available. This constraint defines the GTS availability and provenance contract.

\subsection{Interface and Interaction}

Time-series interfaces extend the general action schema with temporal arguments: as-of time, forecast origin, horizon, frequency, window, channel, unit, and revision. A slice action must state its interval; an aggregation must state its calendar and timezone; and a forecast must state the origin and horizon. TS-Agent \citep{tsagent2025} exposes executable temporal analysis requests, TimeART \citep{timeart2026} structures the request and result objects, and TSAG \citep{tsag2026} couples temporal questions to operations such as trend detection and correlation. These systems turn temporal meaning into an explicit interface contract.

The temporal specialization of a tool call is therefore
\begin{equation}
  \omega_k^{\mathrm{TS}}=(\operatorname{op}_k,[t_k^{-},t_k^{+}],f_k,c_k,u_k,\tau_k),
  \label{eq:gts-temporal-action}
\end{equation}
where the interval, frequency, channel set, units, and reference time are explicit action fields.

\subsection{Memory and Context}

Temporal memory preserves time-indexed state, missingness, provenance, data vintage, event history, and revision records. The state remains queryable as it was known at a declared time, giving it semantics beyond an ordinary conversation buffer. TIMECLAW \citep{timeclaw2026harness} stores execution trajectories and multimodal experience; ForecastCompass \citep{forecastcompass2026} retrieves adaptive forecasting context; and FinMem \citep{finmem2023} organizes financial evidence into layered memories. MemCast \citep{memcast2026} uses hierarchical temporal experience to guide forecast refinement. Their common GTS contribution is the temporal key attached to memory: an event or trajectory is usable only when its availability, vintage, and revision status are known.

For any temporal object $z$ retrieved or produced at $\tau$, the GTS validity predicate is
\begin{equation}
  \operatorname{Valid}_{\mathrm{TS}}(z;\tau)=\mathbb{1}\!\left[\operatorname{Avail}(z)\subseteq\mathcal{I}_{\tau}\;\wedge\;\operatorname{Align}(z)=1\;\wedge\;\operatorname{Unit}(z)=1\right].
  \label{eq:gts-validity}
\end{equation}
This predicate is what turns temporal provenance, alignment, and unit semantics into an executable module boundary.

\subsection{Tools and Execution}

Time-series tools implement temporal slicing, resampling, aggregation, decomposition, backtesting, forecasting, anomaly localization, imputation, and context alignment. Their semantics must specify intervals, horizons, time zones, units, and missing-data behavior. TimeSeriesScientist \citep{timeseriesscientist2025} and TimeCopilot \citep{timecopilot2025} expose model and analysis selection as callable operations. Argos \citep{argos2025} binds monitoring operations to a temporal metric workspace, while AnomaMind \citep{anomamind2026} connects detection, localization, diagnosis, and numerical diagnostics. The temporal tool boundary is where numerical fidelity and chronological admissibility become executable checks. A temporal tool therefore returns an object tied to the declared interval and reference time:
\begin{equation}
  o_{k+1}^{\mathrm{TS}}=\operatorname{Exec}_{n_k}\!\left(x_{[t_k^{-},t_k^{+}]},f_k,c_k,u_k,\tau_k\right).
  \label{eq:gts-tool-output}
\end{equation}

\subsection{Control, Verification, and Feedback}

Temporal control checks chronological splits, allowed-context policies, leakage, units, frequency, drift, uncertainty, and evidence completeness. A validator can reject a future-leaking retrieval, an invalid window, an inconsistent unit conversion, or an unsupported probabilistic claim before the result reaches a user. AION \citep{aion2026} exposes validation interfaces and layered review; VeriTime \citep{veritime2026} tests temporal validity conditions; and TraceBench \citep{tracebench2026} records intervention-aware trajectories for root-cause attribution. These checks define the GTS contract independently of the final task metric. A temporal result is released when its availability, alignment, and unit checks all pass:
\begin{equation}
  g_k^{\mathrm{TS}}=\mathbb{1}\!\left[\operatorname{Avail}(r_k)\subseteq\mathcal{I}_{\tau_k}\;\wedge\;\operatorname{Align}(r_k)=1\;\wedge\;\operatorname{Unit}(r_k)=1\right].
  \label{eq:gts-control}
\end{equation}

\subsection{Planning and Workflow}

Temporal workflows schedule rolling-origin evaluation, horizon-aware model selection, context retrieval by availability time, forecast revision, incident escalation, and report generation. ATSF \citep{atsf2026} makes perception, planning, action, reflection, and memory an iterative forecasting loop. AION \citep{aion2026} binds task files to temporal workspaces and validation artifacts, while ForecastCompass \citep{forecastcompass2026} combines adaptive memory with model selection and forecast revision. The GTS contribution is the temporal checkpoint carried through each planning step. For rolling-origin planning, each candidate workflow is evaluated at origins that precede its corresponding horizon:
\begin{equation}
  \mathcal{O}=\left\{(\tau_j,\tau_j+H):j=1,\ldots,J\right\},\qquad
  \rho^{\star}=\arg\max_{\rho}\sum_{j=1}^{J}\operatorname{Score}\left(\rho;\tau_j,\tau_j+H\right).
  \label{eq:gts-rolling-plan}
\end{equation}

\subsection{Optimization and Evolution}

Temporal optimization uses regimes, temporal experience, shifting distributions, and revision outcomes to update prompts, tools, memories, or policies. TIMECLAW \citep{timeclaw2026explore} evolves capabilities from evaluated trajectories; MetaCaster \citep{metacaster2026} searches over generated forecasters; CastFSR \citep{castfsr2026} adapts retrieval and reflection to the current series; and CRAFTER \citep{crafter2026} validates proposed temporal features. CastFSR gives the temporal loop a precise state and action semantics. Its state combines the task, memory, current forecast prior, and retrieved context, and its policy chooses among fast, slow, reflective, and final actions:
\begin{equation}
  s_k=\Phi(I,M_k,\widehat{Y}^{\mathrm{prior}}_k,C_k),\qquad
  a_k\sim\pi_{\theta}(\cdot\mid s_k),\quad a_k\in\mathcal{A}_{\mathrm{fast}}\cup\mathcal{A}_{\mathrm{slow}}\cup\mathcal{A}_{\mathrm{reflect}}\cup\mathcal{A}_{\mathrm{final}}.
  \label{eq:castfsr-state-action}
\end{equation}
The same paper defines the temporal context and revision stages as
\begin{equation}
\begin{aligned}
  C_k&=T_{\mathrm{ctx}}(D_{\mathrm{task}},D_{\mathrm{domain}},X_{1:L},H_{\mathrm{ctx}},\widehat{Y}^{\mathrm{prior}}_k,M_k;W_k),\\
  \widehat{Y}^{\mathrm{cand}}_k&=G_{\theta}(\widehat{Y}^{\mathrm{prior}}_k,C_k,M_k),\\
  E_k&=E_{\theta}(\widehat{Y}^{\mathrm{cand}}_k,\widehat{Y}^{\mathrm{prior}}_k,C_k,M_k),\qquad
  \widehat{Y}_{1:H}=F_{\theta}(\widehat{Y}^{\mathrm{cand}}_k,E_k,M_k).
\end{aligned}
\label{eq:castfsr-revision}
\end{equation}
These equations make the GTS contribution concrete: the Agent revises a numerical prior with horizon-aligned context and releases it only after temporal, contextual, and domain checks \citep{castfsr2026}. The GTS condition is that promotion and rollback remain valid under temporal shift. A temporal component is promoted only when it passes held-out checks across the evaluated regimes:
\begin{equation}
  \operatorname{Promote}(\phi)=\mathbb{1}\!\left[\min_{r\in\mathcal{R}_{\mathrm{heldout}}}\operatorname{Score}(\phi;r)\geq\delta\right].
  \label{eq:gts-promotion}
\end{equation}

\subsection{Coordination and Scaling}

Multi-agent temporal coordination shares aligned series, event windows, provenance, and evidence identifiers across numeric, visual, textual, planning, and review roles. MAS4TS \citep{mas4ts2026} separates temporal analysis roles, FinCon \citep{fincon2024} coordinates financial analysts and a manager, and ClimateAgent \citep{climateagent2025} joins data, code, visualization, and report agents. The GTS requirement is a common temporal state: Aligned timestamps and provenance keep coordinated conclusions temporally consistent. For role outputs $z_k^{(j)}$, the shared state keeps only temporally compatible evidence:
\begin{equation}
  z_k^{\mathrm{shared}}=\operatorname{Merge}\left(\left\{z_k^{(j)}:\operatorname{Align}(z_k^{(j)},\mathcal{I}_{\tau_k})=1\right\}_{j=1}^{J}\right).
  \label{eq:gts-coordination}
\end{equation}

\subsection{Cross-dimensional temporal requirements}

The seven dimensions jointly enforce six recurring requirements:

\begin{itemize}
  \item \textbf{Temporal causality}: earlier states, actions, retrievals, and evaluations use observations, labels, events, and revisions available at that time.
  \item \textbf{Numerical fidelity}: values, scales, units, timestamps, and precision survive representation and tool boundaries.
  \item \textbf{Time-indexed state integrity}: alignment, missingness, channels, provenance, and data vintage remain available and auditable.
  \item \textbf{Temporal operation semantics}: slicing, resampling, aggregation, forecasting, localization, and metric operations have explicit interval and horizon semantics.
  \item \textbf{Temporal grounding}: external context is bound to the relevant interval, lag, horizon, availability time, provenance, and causal assumptions.
  \item \textbf{Output auditability}: analytical outputs expose a task-appropriate checker, metric, evidence trace, or review protocol, with uncertainty validation when probabilistic semantics apply.
\end{itemize}

These requirements form the cross-task design checklist; the next section instantiates them under four task contracts.
\section{Task-Specific Time-Series Harness}
\label{sec:task-specific-harness}

Task-specific Harness modules instantiate the General Time-Series Harness under a concrete output contract. Four task families organize this section, each analyzed through interface, memory, tools, control and verification, planning, optimization, and coordination.

The task contract determines the final object being optimized. For forecasting, a typical contract is
\begin{equation}
  \widehat{y}_{\tau+1:\tau+H}=f_\theta\!\left(y_{\leq\tau},x_{\leq\tau}\right),
  \label{eq:forecast-contract}
\end{equation}
where $H$ is the declared horizon and the inputs are restricted by the availability set in Eq.~\ref{eq:temporal-availability}.

\subsection{Forecasting and Prediction}

Forecasting agents manage horizons, chronological splits, model selection, probabilistic outputs, revision, and deployment constraints. AIA Forecaster combines agentic search, supervisor aggregation, and statistical calibration for judgmental event forecasts \citep{aiaforecaster2025}; AUDITFORECAST makes the update path explicit by anchoring a forecast with a quantitative baseline and applying situational updates in odds space \citep{auditforecast2026}. The interface exposes the forecast origin, horizon, frequency, and target channels; memory preserves point-in-time covariates, prior forecasts, and revisions; and tools provide model fitting, backtesting, ensembling, and reconciliation. TimeSeriesScientist \citep{timeseriesscientist2025} constructs a role-based forecasting workflow, TimeCAP \citep{timecap2025} adds contextual augmentation, and TimeCopilot \citep{timecopilot2025} selects among forecasting models as callable tools. Last-Mile Forecasting \citep{lastmile2026} focuses on decision-ready revision, HydroAgent \citep{hydroagent2026} couples hydrological simulation with warnings, and CastFlow \citep{castflow2026} iteratively refines forecasts using multi-view evidence. The TSK contract is the horizon-specific output together with leakage-controlled validation and revision rules. For a candidate model set $\mathcal{M}$, the forecasting workflow selects the model and forecast jointly under rolling-origin evaluation:
\begin{equation}
  m^{\star}=\arg\min_{m\in\mathcal{M}}\frac{1}{J}\sum_{j=1}^{J}\ell\left(\widehat{y}^{(m)}_{\tau_j+1:\tau_j+H},y_{\tau_j+1:\tau_j+H}\right).
  \label{eq:forecast-model-selection}
\end{equation}

\subsection{Data Augmentation and Synthesis}

Augmentation and synthesis agents generate, select, or validate temporal data and representations. BRIDGE \citep{bridge2025} conditions temporal generation on language and evaluates the generated series; MERIT \citep{merit2025} combines similar-series retrieval, augmentation, and review; and SCENARIODIFF \citep{scenariodiff2026} generates forecast-relevant scenarios from multimodal anchors. SCENARIODIFF separates the agents that summarize historical evidence, generate a scenario description, and produce sparse anchor points, then conditions a diffusion forecaster on those signals. Its conditional denoising objective is
\begin{equation}
  \mathcal{L}(\theta)=\mathbb{E}_{x^{(0)},t,\epsilon}
  \left\|x^{(0)}-x_{\theta}\!\left(x^{(t)},t,c\right)\right\|_2^2,
  \qquad
  x^{(t)}=\sqrt{\bar\alpha_t}x^{(0)}+\sqrt{1-\bar\alpha_t}\,\epsilon,
  \label{eq:scenariodiff-denoising}
\end{equation}
where $c$ contains the historical summaries and scenario context \citep{scenariodiff2026}. The interface declares the conditioning window, channels, sampling frequency, and intended use; memory records source series, transformations, and provenance; and verification compares temporal dependence, missingness, distributional fidelity, and downstream utility. The TSK contract is the generator--validator loop with temporal fidelity and downstream utility checks.

For a conditioning context $\mathcal{C}$, a synthesis module produces a candidate series and is accepted only when its temporal fidelity and downstream utility satisfy the declared checks:
\begin{equation}
  \widetilde{x}_{1:T}\sim p_{\phi}(x_{1:T}\mid\mathcal{C}), \qquad
  \operatorname{Accept}(\widetilde{x})=\mathbb{1}\!\left[\mathcal{F}(\widetilde{x},x)\geq\delta_f\;\wedge\;\mathcal{U}(\widetilde{x})\geq\delta_u\right].
  \label{eq:augmentation-contract}
\end{equation}

\subsection{Anomaly Detection and Diagnosis}

Anomaly agents localize events, propose or verify rules, retrieve incident evidence, diagnose causes, and support remediation. AnomaMind \citep{anomamind2026} separates coarse evidence acquisition, adaptive evidence construction, detection, and iterative refinement. ChatAD \citep{chatad2026} uses language-guided anomaly reasoning, while SAGE-AD \citep{sagead2026} and LEMAD \citep{ji2025lemad} connect detection to diagnosis and service context. Large-model-based smart agents \citep{wang2026large} use temporal evidence to interpret power-system anomalies. The TSK contract fixes monitoring windows, thresholds, root-cause labels, false-alarm budgets, alert policies, and deployment gates. AnomaMind makes the sequential structure explicit: at step $k$, the agent maintains a state $s_k$, selects an action $a_k$, and receives numerical or knowledge evidence $o_k$ from its toolkit. Its toolkit is written as $B=\{K,N\}$, where $K$ denotes knowledge memory and $N$ numerical diagnostics. The paper's workflow update and detector are
\begin{equation}
  s_{k+1}=E\!\left(s_k,a_k,o_k,\widehat{Y}^{(k)}\right),\qquad
  \widehat{y}_j=D_{\theta}\!\left(s_j,Z_{1:k},C_{1:k}\right),\quad \widehat{y}_j\in\{0,1\},
  \label{eq:anomamind-decision}
\end{equation}
and its rule-based feedback combines parse validity, interval F1, and a false-positive penalty,
\begin{equation}
  r_k=\lambda_p r_k^{\mathrm{parse}}+\lambda_f r_k^{F1}-\lambda_{fp}r_k^{FP},\qquad
  \max_{\theta}\;\mathbb{E}_{\widehat{Y}^{(k)}\sim\pi_{\theta}(\cdot\mid s_k)}\left[\sum_{k=1}^{K}r_k\right].
  \label{eq:anomamind-reward}
\end{equation}
This is the method-level distinction: the LLM gathers evidence and reflects, while the detection policy receives task-specific learning signals \citep{anomamind2026}. Anomaly detection therefore proceeds through evidence-seeking decisions, tool responses, and state updates rather than a single fixed score.

\subsection{Decision Support}

Decision-support agents connect forecasts or diagnoses to actions under costs, constraints, uncertainty, and review requirements. Prediction-market theory makes the forecast-to-action link explicit: a forecast becomes useful through a market-dependent scoring and betting rule, which is a complementary decision contract for agent evaluation \citep{prophets2026}. FinCon \citep{fincon2024} coordinates analyst evidence before portfolio decisions, TradingAgents \citep{tradingagents2024} turns market and news analysis into risk-aware trading actions, and CoLLMLight \citep{collmllight2026} uses simulation feedback for network-wide signal control. ClimateAgent \citep{climateagent2025} connects climate analysis to operational workflows, while Smart Energy Agent \citep{smartenergyagent2026} converts appliance-level anomalies into maintenance recommendations. FinCon states the decision objective directly as cumulative profit and loss under prompt-controlled analyst and manager policies,
\begin{equation}
  \max_{\theta}\;\mathbb{E}\!\left[\sum_{t\in\mathcal{T}}\alpha^t R_t^{\Pi_{\theta}}\right],
  \qquad R_t^{\Pi_{\theta}}=R(O_t,B_t,A_t),
  \label{eq:fincon-objective}
\end{equation}
and its portfolio manager solves a mean--variance allocation subject to the buy/sell/hold direction selected by the agents,
\begin{equation}
  \max_{w}\;\langle w,\mu\rangle-\langle w,\Sigma w\rangle,\qquad
  w_n\in\begin{cases}[0,1],&\text{buy},\\\left[-1,0\right],&\text{sell},\\\{0\},&\text{hold},\end{cases}
  \quad n=1,\ldots,N.
  \label{eq:fincon-portfolio}
\end{equation}
These equations show how the multi-agent Harness turns temporal evidence into a task-specific action and risk contract \citep{fincon2024}. The TSK interface represents the current state, available actions, timing, and authority; control checks risk limits and counterfactual consequences; and human review records whether the recommendation was accepted, revised, or escalated.

Decision support extends prediction through an action utility:
\begin{equation}
  a_{\tau}^{\star}=\arg\max_{a\in\mathcal{A}}\mathbb{E}\!\left[U(a,Y_{\tau+1})\mid\mathcal{I}_{\tau}\right],
  \label{eq:decision-contract}
\end{equation}
where the utility, action set, uncertainty, and review authority are part of the task contract. This makes the transition from forecasting to decision support explicit.

The complete corpus is multi-label across components: a work may contribute to several Harness dimensions and task families, with each component assigned to its deepest applicable Harness layer. The maintained ledger records both the inclusive evidence fields and the exclusive plotting labels, alongside the independent LLM-side contribution.
\section{Infrastructure and Benchmarks for Time-Series Agents}
\label{sec:evaluation}

A Time-Series Agent requires evaluation at three levels: General Harness process, time-series contract, and task outcome. Existing resources cover fragments of this contract; the benchmark gap is the absence of a widely adopted cross-task suite that evaluates them together. AION makes the missing task contract explicit by representing a next-generation time-series task as
\begin{equation}
  \mathcal{T}=(\phi,\mathcal{W},\mathcal{V}),\qquad
  \phi=(\mathcal{T}_{\mathrm{access}},\Sigma,\mathcal{O},\mathcal{C},\mathcal{A}),\qquad
  (g,s)=\mathcal{V}(o),
  \label{eq:aion-task-contract}
\end{equation}
where the task file specifies access, prior knowledge, output form, constraints, and metrics, while the validation interface returns validity checks $g$ and scores $s$ for a candidate output $o$ \citep{aion2026}. This formalization is why a benchmark must expose the workspace and validation interface rather than only a dataset and one score.

\subsection{Evaluation contract}

Evaluation should report tool-call validity, trace faithfulness, memory and artifact provenance, temporal availability rules, numerical fidelity, temporal operations, evidence grounding, task metrics, cost, failures, and revision behavior. A forecast or QA score is one task result within a complete Agent evaluation.

The unit of evaluation is an episode. An episode records the task specification, as-of boundary, visible context, tool calls, intermediate artifacts, validator decisions, revision steps, final output, and resource use. This record attributes errors to prediction, tool selection, leakage, temporal operations, or revision after feedback.

We represent an episode as
\begin{equation}
  e=\bigl(\mathcal{C}_{\mathrm{task}},\tau,\mathcal{I}_{\tau},\omega_{1:K},\mathcal{V}_{1:K},r,\operatorname{Cost}(e)\bigr),
  \label{eq:episode-record}
\end{equation}
which keeps the task contract, information boundary, execution trace, verification decisions, final result, and resource use in one auditable record. A benchmark reports a vector of process validity, temporal-contract validity, task outcome, and resource behavior:
\begin{equation}
  \mathcal{E}(e)=\bigl(E_{\mathrm{GH}},E_{\mathrm{GTS}},E_{\mathrm{TSK}},E_{\mathrm{resource}}\bigr),
  \label{eq:evaluation-vector}
\end{equation}
where the four coordinates measure process validity, temporal-contract validity, task outcome, and cost or failure behavior. The vector follows the construction hierarchy and makes clear which layer a benchmark actually tests.

The same protocol should support controlled perturbations: hide or reveal contextual evidence, shift the forecast origin, inject missingness, change the frequency, or replace a tool with a failing implementation. These interventions expose whether a system relies on the intended temporal evidence and whether its General Harness can recover from operational failures.

TSQA and multimodal QA provide evidence for grounded temporal answers within the broader Agent contract.

\subsection{Role of QA within a Time-Series Agent benchmark}

QA resources evaluate temporal answers, evidence grounding, and selected numerical reasoning. They provide the language-facing part of evaluation; a complete Agent benchmark adds chronological validity, numerical fidelity, forecasting-horizon behavior, anomaly localization, augmentation quality, downstream decision utility, tool-call correctness, memory provenance, and validation traces.

\subsection{Infrastructure and the missing unified benchmark}

FutureSim adds a replayable world-event environment in which an Agent can be evaluated under changing information and adaptive interaction, complementing dataset-fixed forecasting benchmarks \citep{futuresim2026}. WorldReasoner focuses on whether a forecasting Agent respects the information available at prediction time and whether its reasoning is valid, making temporal leakage and trace quality explicit benchmark targets \citep{worldreasoner2026}. TimeClaw, AION, TimeSeriesGym, and ModernTSF provide complementary infrastructure. ModernTSF contributes an agent-ready and reproducible forecasting substrate with model and dataset catalogs, callable interfaces, evidence, budgets, artifacts, and recoverable execution \footnote{ModernTSF repository: \url{https://github.com/Diaugeia/ModernTSF}.}. It provides an infrastructure case for the benchmark stack. A unified public suite would combine a time-indexed availability policy, executable temporal tools, trace and evidence validation, and task contracts across forecasting, augmentation, anomaly diagnosis, and decision support.

A reusable benchmark stack should therefore include a time-indexed workspace, explicit availability rules, executable temporal tools, trace and evidence schemas, validators, cases from all four task families, and cost, failure, and revision logs. These requirements connect the infrastructure chapter to the open problems below.
\section{Open Problems and Focused System Analyses}

\subsection{Reusable temporal infrastructure}

Time-Series Agents need shared workspaces, temporal tool contracts, evidence schemas, validators, and reproducible execution. ModernTSF, TimeClaw, AION, and related projects show complementary pieces of this stack. A reusable workspace binds data, tools, traces, and validators to one point-in-time state:
\begin{equation}
  \mathcal{W}_{\tau}=\left(\mathcal{D}_{\leq\tau},\mathcal{T},\mathcal{R}_{\tau},\mathcal{V},\mathcal{A}_{\tau}\right),
  \qquad \mathcal{R}_{\tau}=\operatorname{Run}(\mathcal{W}_{\tau},\pi_{\theta}).
  \label{eq:infrastructure-workspace}
\end{equation}

\subsection{Open problems}

The module ledger makes these open problems explicit. Each card separates the claim, module, task contract, and evidence, so gaps appear as missing or weakly supported regions in the research map. Across the reviewed cards, the clearest gaps occur at the interfaces between layers: model-side temporal understanding is rarely connected to auditable Harness state; reusable temporal modules are often evaluated through a single task; and task-specific systems seldom report decision feedback, revision behavior, or deployment cost. New papers can therefore be assessed by asking which card field or module they strengthen and which previously unsupported contract they make measurable.

\noindent\textbf{Temporal and numerical faithfulness.} Agents need typed temporal operations, unit-aware representations, chronology guards, and end-to-end fidelity checks. A textual explanation is reliable when tools preserve frequency, precision, and forecast-origin constraints. Future systems should validate numerical and temporal invariants at every interface alongside the final answer. For an operation $o$ applied at time $\tau$, the invariant is
\begin{equation}
  \operatorname{Faithful}(o;\tau)=\mathbb{1}\!\left[\operatorname{Time}(o)\subseteq\mathcal{I}_{\tau}\;\wedge\;\operatorname{Unit}(o)=1\;\wedge\;\operatorname{Value}(o)=1\right].
  \label{eq:open-faithfulness}
\end{equation}

\noindent\textbf{Context retrieval and memory with temporal provenance.} Retrieved events and episodic memories need availability-time provenance, expiry, regime awareness, and replayable audits. This problem links GTS memory to evaluation: an Agent should be able to reconstruct exactly which event, revision, or prior trajectory was visible when a decision was made. A replayable retrieval is defined by its query, availability boundary, and returned evidence:
\begin{equation}
  \operatorname{Replay}(q,\tau)=R_{\psi}\left(\mathcal{M}_{\leq\tau},q\right),
  \qquad \operatorname{Prov}(m)=\left(t_{\mathrm{event}},t_{\mathrm{avail}},t_{\mathrm{rev}}\right).
  \label{eq:open-memory-provenance}
\end{equation}

\noindent\textbf{Interface standardization.} Shared schemas for temporal workspaces, tools, traces, and validators would make systems composable and comparable. A common contract aligns as-of policies, window semantics, and failure handling across Agents. A standard temporal tool schema can be represented as
\begin{equation}
  \mathcal{S}_{\mathrm{tool}}=\left(n,\operatorname{Args},\operatorname{Ret},\operatorname{Time},\operatorname{Perm},\operatorname{Fail}\right).
  \label{eq:open-tool-schema}
\end{equation}

\noindent\textbf{Self-evolving components.} Tool, policy, memory, and workflow updates require regression checks under temporal shift. Capability evolution should preserve previous generations when a new component fails held-out temporal checks, and should record the evidence that justified promotion. For a candidate component $\phi'$, promotion requires improvement on held-out temporal episodes without violating a regression bound:
\begin{equation}
  \operatorname{Promote}(\phi')=\mathbb{1}\!\left[\Delta E_{\mathrm{heldout}}(\phi')\geq\delta \;\wedge\; \Delta E_{\mathrm{regress}}(\phi')\leq\epsilon\right].
  \label{eq:open-evolution}
\end{equation}

\noindent\textbf{Decision-centric evaluation.} Future benchmarks should connect predictive or diagnostic evidence to action quality, cost, uncertainty, and accountability. Prediction informs action; an Agent benchmark should measure whether a forecast or diagnosis changes a decision appropriately under explicit constraints, alongside prediction accuracy. A decision episode couples the predictive distribution to an action utility:
\begin{equation}
  a_{\tau}^{\star}=\arg\max_{a\in\mathcal{A}}\mathbb{E}\left[U(a,Y_{\tau+1})\mid\mathcal{I}_{\tau}\right]-\lambda\operatorname{Cost}(a).
  \label{eq:open-decision-utility}
\end{equation}

\subsection{Focused system analyses}

\noindent\textbf{ChatTS: changing the LLM side.} ChatTS equips a language model with temporal values and attributes through a multimodal input pipeline. Its attribute selector, synthetic time-series/text generator, evolution-instruct stage, and multimodal model align numerical series with language supervision \citep{chatts2025}. In our ledger this is an LLM-side contribution with a General Time-Series Harness binding: the learned alignment is reusable across temporal questions, while the dialogue and reasoning tasks provide task-specific instantiations. The central evidence is the change in what the LLM can represent and explain, together with the synthetic-data assumptions shown in Fig.~\ref{fig:chatts-overview}.

\noindent\textbf{TimeClaw: making temporal semantics executable.} TimeClaw turns the GTS boundary into a runtime: numerical execution remains server-side, temporal tools evolve through an evaluated toolbox, and solution trajectories remain auditable and reusable \citep{timeclaw2026explore}. Its method is an explicit Explore--Compare--Distill--Reinject loop. For a task instance $x$, candidate executions are scored by task loss and the best valid trajectory is selected:
\begin{equation}
  q(\pi_k;x)=-L_{\tau}(\widehat{y}_k,y^{\star}),\qquad
  \pi^{\star}(x)=\arg\max_{\pi_k\in\Pi_{\mathrm{valid}}(x)}q(\pi_k;x).
  \label{eq:timeclaw-compare}
\end{equation}
The selected execution is summarized, cleaned to remove answer leakage and non-transferable control text, and distilled into an external experience state:
\begin{equation}
  n_x=\operatorname{Summarize}\!\left(x,\Pi(x),\{q(\pi_k;x)\}_{k=1}^{K},\pi^{\star}(x)\right),\quad
  e_x=\operatorname{Clean}(n_x),\quad
  A_s^{(m+1)}=\operatorname{Distill}\!\left(A_s^{(m)},e_x\right).
  \label{eq:timeclaw-distill}
\end{equation}
These equations capture the paper's concrete contribution: execution quality, rather than completion alone, determines which temporal tool trajectory becomes reusable experience \citep{timeclaw2026explore}.

\noindent\textbf{ModernTSF: infrastructure and reproducibility.} ModernTSF represents the infrastructure contribution: callable model and dataset interfaces, evidence, budgets, artifacts, and recoverable execution provide a foundation for reproducible Agent evaluation \footnote{ModernTSF repository: \url{https://github.com/Diaugeia/ModernTSF}.}. Its role in this survey is to specify what a benchmark must make executable and inspectable: data and model identity, tool inputs and outputs, budgets, intermediate artifacts, and recoverable failures. It complements the benchmark resources in Table~\ref{tab:benchmark-families} and supplies the infrastructure layer for a unified cross-task evaluation protocol. The reproducible record is
\begin{equation}
  \mathcal{A}_{\mathrm{run}}=\left(\operatorname{ID}_{\mathcal{D}},\operatorname{ID}_{\mathcal{M}},\omega_{1:K},\operatorname{Artifacts},\operatorname{Budget},\operatorname{Failures}\right).

\end{equation}

\section{Conclusion}

A Time-Series Agent is built by combining an LLM, a General Harness, and a Time-Series Harness Module. The survey separates the model-side contribution from the runtime contribution, organizes the General Harness through seven shared dimensions, extracts genuinely temporal mechanisms into the General Time-Series Harness, and instantiates them under forecasting, augmentation, anomaly diagnosis, and decision support. Evaluation then follows the same construction: process, temporal contract, and task outcome. The remaining research challenge is to make these layers interoperable and to evaluate them with a unified, reproducible benchmark.
