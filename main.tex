\textbf{Abstract.}
Time-series analysis increasingly combines predictive models with LLM agents that retrieve temporal context, call analytical tools, validate intermediate results, and revise decisions. This survey asks how such systems are constructed from an LLM and its surrounding Harness. We first classify the general Harness using concepts synthesized from Harness surveys; we then separate the Time-Series Harness into mechanisms that generalize across temporal tasks and mechanisms tied to a particular task. Task categories enter at this point as the natural basis for identifying task-specific contracts. We use this framework to compare the contributions of 82 reviewed works and organize evaluation from agent execution to temporal consistency and task performance. The resulting synthesis identifies opportunities for reusable temporal infrastructure, reliable memory and tool use, component adaptation, and downstream decision support.
\end{tcolorbox}

\textbf{Keywords}: time series agents, LLM agents, temporal reasoning, time series foundation models, contextualized time series, tool use, memory, benchmark, harness.

\section{Introduction}

Time series analysis has long been organized around task-specific predictors: forecasting, classification, anomaly detection, imputation, segmentation, and representation learning. This model-centric paradigm has produced a mature ecosystem spanning classical statistical methods, deep neural architectures, foundation models, and LLM-enhanced temporal models \citep{zhang2024llmts,jiang2024empowering}. These systems are essential, but most of them are designed to answer a bounded modeling question once the task, data split, features, context, and evaluation protocol have already been specified.

The task space is broader than forecasting. Time-series systems may be asked to forecast future values, classify sequence-level or window-level labels, detect anomalies and root causes, impute missing observations, answer questions about temporal evidence, retrieve event context, generate benchmarks, revise deployed forecasts, or support downstream decisions. These tasks share temporal constraints, but they do not require identical runtime components. A forecasting agent needs horizon-aware validation, model selection, ensembling, and revision contracts; an anomaly agent needs window localization, rule generation, and incident evidence; a classification agent needs channel-aware evidence and class exemplars; a QA agent needs faithful tool calls and answer grounding. This task heterogeneity is why a single undifferentiated time-series module is too coarse.

However, real temporal analysis rarely ends with a single model output~\cite{promptstoagents2026,chen2026tsagentsurvey,xu2026forecastagentsurvey,aion2026,timeclaw2026harness}. A practitioner must inspect data quality, verify temporal granularity, identify regime shifts, retrieve events, select tools, compare models, validate against chronological splits, explain evidence, revise forecasts under constraints, and turn predictions into operational decisions. These steps require a system-level runtime, not only a stronger backbone model.

LLM agents provide a natural system abstraction for this broader workflow. In the general agent literature, the runtime around an LLM provides external computation, action schemas, tools, memory, state, execution loops, validators, observability, and permission boundaries \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness}. We describe LLM-based agents through the following runtime abstraction:

The LLM supplies language understanding, planning, and judgment; the general runtime supplies the interface and control surfaces that make actions executable, stateful, auditable, and revisable. Time series add a domain layer that a generic agent does not automatically provide. Temporal workflows expose recurring failure modes involving chronological admissibility, frequency and unit semantics, temporal alignment, and output auditability; related concerns such as missingness, non-stationarity, and uncertainty cut across these obligations rather than forming independent taxonomy axes. The \TSHarnessModule{} is therefore the part of the system that makes temporal objects native to the agent runtime rather than treating them as ordinary text. We further divide it into two levels: a \GeneralTSHarness{} that is useful across time-series tasks, and a \TaskSpecificHarness{} that is tied to forecasting, anomaly detection, classification, QA, imputation, benchmark generation, or another concrete task family.

A mechanism belongs to GH when its design remains useful beyond time-series applications without relying on temporal assumptions. The Harness then specializes into a Time-Series Harness Module. Within that module, a mechanism belongs to GTS when it is reusable across the relevant temporal task settings, and to TSK when its state, actions, rewards, or verification are tied to one task contract. Identifying TSK therefore requires knowing which temporal task contracts exist; task taxonomies from prior surveys provide that downstream structure.

These judgments apply to mechanisms rather than entire papers: one system can combine general memory and reflection, cross-task temporal tools, and a forecasting-specific validation loop. Changing from financial forecasting to traffic forecasting changes the application domain but preserves the forecasting task family; it therefore does not by itself establish cross-task generality.

\subsection{Position relative to existing surveys}

Existing surveys cover important subsets of the landscape. Classical and deep-learning surveys organize time-series research around forecasting, change-point detection, anomaly detection, and neural architectures \citep{lim2021deepts,aminikhanghahi2017changepoint,darban2024anomaly,wen2023transformers}. Surveys on time-series foundation models, synthetic data, LLM integration, and multimodal temporal modeling summarize pretraining, adaptation, serialization, prompting, tokenization, cross-modal alignment, data generation, and evaluation \citep{liang2024foundation,liu2025synthetic,zhang2024llmts,jiang2024empowering,liu2025crossmodality,jiang2025multimodal}.

Among the closest related surveys, From Prompts to Agents and Chang et al. provide useful accounts of agentic time-series systems. From Prompts to Agents organizes systems through planning, reasoning, memory, tool use, and self-refinement \citep{promptstoagents2026}; Chang et al. describe reasoning topologies, objectives, and mechanism tags \citep{changsurvey2026}. Chen et al. organize the task-facing literature into forecasting and reasoning, augmentation and synthesis, anomaly detection and diagnosis, and decision support \citep{chen2026tsagentsurvey}. These surveys supply the prior component and task vocabularies from which our framework is built. We use Harness literature to define what an Agent runtime contains, then use time-series task structure to determine whether a temporal mechanism is cross-task or task-specific. Our contribution is the resulting hierarchical organization rather than a parallel task taxonomy.

Several system and position papers further motivate this runtime perspective. ATSF reframes forecasting as an iterative perception--planning--action--reflection--memory process rather than a static predictor \citep{atsf2026}. AION formalizes realistic time-series tasks through task files, workspaces, validation interfaces, artifacts, and layered review \citep{aion2026}. TimeClaw implements a time-series-native runtime with executable tools, episodic multimodal memory, auditable trajectories, and experience-driven capability evolution \citep{timeclaw2026harness}. Building on these systems, we organize the literature by the runtime layer to which each work contributes. We distinguish reusable temporal mechanisms from task-specific workflows and connect these mechanisms to recurring temporal design requirements.

We re-read the broader literature through this additional contribution-locus question. Visible tools, memory, multimodality, decomposition, verification, and agent loops remain useful descriptors, but they do not resolve the locus decision under our protocol. We therefore use an author-normalized, literature-informed 14-component \GeneralHarness{} vocabulary synthesized from general Harness architecture and engineering studies \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness,lin2026agenticharness}. The underlying functions are literature-derived, while the exact 14-way selection, naming, and grouping used here are author-proposed. This vocabulary acts as a control layer, while the temporal obligations and the primary-locus rule provide the domain-specific coding and evaluation lens.

\subsection{Contributions}

This survey makes four contributions.

\begin{enumerate}
  \item We organize Time Series Agents through the hierarchy \GeneralHarness{} $\rightarrow$ \TSHarnessModule{}, with the latter divided into cross-task and task-specific mechanisms.
  \item We use \GeneralHarness{}, \GeneralTSHarness{}, and \TaskSpecificHarness{} as mechanism-level categories that can coexist within a paper. Prior task taxonomies provide the downstream task contracts needed to distinguish GTS from TSK.
  \item We apply the protocol through documented inclusion criteria, an explicit and auditable classification rubric, and a versioned work-level ledger that separates inclusion, primary locus, secondary mechanisms, contribution type, and self-claim metadata.
  \item We synthesize six non-exhaustive temporal design obligations, an auditable component crosswalk, and candidate evaluation routes whose established, adjacent, proposed, and open measurement status is reported explicitly.
\end{enumerate}

\subsection{From LLMs to agents}

For the LLM-based systems in scope, a standalone LLM produces text conditioned on a prompt, whereas we model an agent system as an LLM coupled with a runtime that controls the interaction between model outputs and the external environment. Recent agent-harness literature describes this surrounding layer through reasoning and acting interfaces, environment models, execution environments, tool protocols, context and memory systems, orchestration loops, verification interfaces, observability, governance, and optimization mechanisms \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness,lin2026agenticharness}. The cited works use heterogeneous source units---interface roles, mechanisms, architectural layers, and method-specific editable components---so \emph{component} is our operational umbrella term for a structural-functional vocabulary, not a claim that the sources share one component ontology.

For our purposes, the \GeneralHarness{} contains the same three groups used in Table~\ref{tab:component-vocab}:

\begin{itemize}
  \item \MechanismGroup{}: \Planning{}, \Memory{}, \ToolUse{}, \Control{}, and \HarnessOptimization{} sustain the agent beyond a single generation step \citep{ning2026codeharness,li2026harnesssurvey,lee2026metaharness,lin2026agenticharness}.
  \item \InterfaceGroup{}: \Reasoning{}, \Acting{}, \EnvironmentModeling{}, \ExecutionEnvironment{}, and \StateArtifacts{} define what the agent can represent, execute, and persist \citep{ning2026codeharness,li2026harnesssurvey,lee2026metaharness,lin2026agenticharness}.
  \item \OperationGroup{}: \Lifecycle{}, \Verification{}, \Observability{}, and \MultiAgentScaling{} organize long-horizon execution, review, governance, and collaboration \citep{li2026harnesssurvey,ning2026codeharness,lin2026agenticharness}.
\end{itemize}

This decomposition is domain-agnostic. It describes the functions represented in the in-scope general runtime, while the domain module specifies what a time-series runtime should preserve.

\subsection{Why time-series workflows motivate a Time-Series Harness Module}

Time series are often ordered, scale-sensitive, and dependent on temporal context. These properties motivate---but do not logically entail---a non-exhaustive working set of runtime design obligations. The set is an author-proposed engineering synthesis of recurring temporal failure modes, informed by the literature surveyed below; it is not a derivation of a unique six-element ontology. The component-to-obligation mapping is many-to-many. Individual obligations apply only when their preconditions hold, such as a prospective information boundary, exact numerical semantics, the use of external context, or an output with probabilistic meaning. Missingness is handled within time-indexed state, uncertainty within output auditability when applicable, and non-stationarity across state and validation rather than as additional taxonomy axes. The six design obligations are:

\begin{itemize}
  \item \keyterm{Temporal causality}: when a prospective or as-of-time information boundary exists, future observations, labels, events, and revisions must not enter earlier state, actions, retrieval, decisions, or evaluation.
  \item \keyterm{Numerical fidelity}: when values, units, scales, timestamps, or precision affect the declared semantics, representations and interfaces should preserve them within a stated tolerance.
  \item \keyterm{Time-indexed state integrity}: when temporal objects persist across runtime steps, timestamps, frequency, missingness, covariates, channels, units, provenance, and revision history should remain semantically available and auditable.
  \item \keyterm{Temporal operation semantics}: time-sensitive operations such as slicing, aggregation, decomposition, smoothing, forecasting, anomaly localization, event alignment, and metric computation should have explicit interval, horizon, and input--output semantics that can be replayed or checked.
  \item \keyterm{Temporal grounding of context}: when textual, visual, tabular, or event context is consumed, it should be bound to the relevant intervals, lags, horizons, availability times, provenance, and causal assumptions.
  \item \keyterm{Output auditability with conditional uncertainty validation}: analytical outputs should expose a task-appropriate validation route, such as an executable checker, metric, evidence trace, or documented human-review protocol. When an output carries probabilistic, confidence, or interval semantics, its uncertainty should additionally be evaluated on a declared reference population using a task-appropriate scoring rule.
\end{itemize}

For compact matrix and summary-table labels, \emph{Output auditability} denotes the full sixth obligation, including conditional uncertainty validation when its probabilistic preconditions hold.

Together, these obligations form a reusable checklist for a \GeneralTSHarness{}. They are grouped by their shared temporal scope and failure consequences, not because they occupy the same ontological layer: their primary enforcement objects span constraints, representations, state, action interfaces, evidence binding, and output verification. An obligation may be marked \emph{not applicable} when its precondition is absent, or \emph{not currently evaluable} when it applies but the available artifact does not expose a valid test; neither status should be counted as a pass.

A second level is task-specific. Forecasting modules introduce horizon contracts, backtesting, model-selection policies, forecast reconciliation, ensembling, and revision ledgers. Anomaly modules introduce localization, incident windows, rule synthesis, root-cause evidence, and deployment gates. Classification modules introduce channel-wise evidence, exemplar memories, label calibration, and confidence aggregation. QA modules introduce temporal question schemas, faithful tool execution, and evidence-grounded answer checking. Imputation modules introduce missingness mechanisms, mask-aware operators, and reconstruction validation; we retain imputation as a reserved task family although the current ledger contains no dedicated imputation-agent system. This is why Time Series Agents are not equivalent to prompting an LLM with a CSV. The \TSHarnessModule{} changes what the LLM can observe, which actions it can take, how intermediate evidence is stored, how outputs are verified, and how experience is reused. The six obligations span the analysis pipeline from data intake to output verification; turning a verified output into an accountable downstream \emph{decision} is the next lifecycle stage and remains an open frontier.

\section{Component Map for Time Series Agents}

The component map follows the hierarchy in Table~\ref{tab:harness-hierarchy}. The \GeneralHarness{} is described by an author-normalized 14-component structural-functional vocabulary synthesized from Harness literature \citep{li2026harnesssurvey,ning2026codeharness,lee2026metaharness,lin2026agenticharness}. The Time-Series Harness Module then specifies which temporal objects, operations, context bindings, and validation requirements the runtime must support. Its cross-task mechanisms form the \GeneralTSHarness{}; its task-bound mechanisms form the \TaskSpecificHarness{}. The task categories reviewed in prior time-series surveys provide the output contracts that make this final distinction concrete. Thus the map proceeds from general runtime components, to temporal specialization, to task-specific instantiation.

\subsection{How the six design obligations specialize the 14 components}

Table~\ref{tab:invariant-component-matrix} is an author-proposed illustrative crosswalk, not an empirical measurement, a validation of the six obligations, or a uniquely determined architecture. The unit of coding is one ordered pair consisting of an obligation and a Harness component. For each pair we ask three questions in order: (Q1) within the component responsibility stated in Table~\ref{tab:component-vocab}, must the component consume or produce an obligation-specific object, field, or rule? If not, the cell is blank. (Q2) Can the component locally prevent, reject, or detect a violation using an explicit criterion? If so, the cell is marked $\bullet$ for direct enforcement or detection. (Q3) Otherwise, does it directly store, transport, schedule, or expose the obligation-specific information for an enforcing component? If so, the cell is marked $\circ$ for a supporting or carrying role; otherwise it is blank. Generic usefulness, a merely possible future specialization, or an effect mediated entirely by another component does not qualify. Ambiguous cells are coded downward ($\bullet\!\rightarrow\!\circ\!\rightarrow$ blank) and retained for review. ``Direct'' is non-exclusive: several components may enforce different boundaries of the same obligation.

\section{Literature Landscape}

\subsection{Temporal models as agent components}

The component-centric view does not discard model-centric time series research. Instead, it changes its role. Classical statistical models, deep forecasters, TSFMs, LLM-based time series models, and multimodal temporal models become callable temporal tools inside the \TSHarnessModule{} \citep{zeng2023dlinear,nie2023patchtst,wu2023timesnet,ansari2024chronos,das2024timesfm,rasul2023lagllama,woo2024moirai,goswami2024moment,timegpt2023,timer2024,jin2024timellm,unitime2024,test2024,urbangpt2024,chattime2025,timevlm2025,timeomnivl2026}. They may provide forecasting, representation learning, sequence generation, multimodal understanding, or domain adaptation. They are not sufficient to define an agent, but they are important capabilities that an agent can select, execute, compare, and verify. One consequence of this synthesis is that prior time-series models need not be treated as competitors to Time Series Agents as a category; they can be embedded as components of a broader agent runtime, consistent with the model-to-agent process view articulated in ATSF \citep{atsf2026}.

This distinction also helps interpret the debate on LLMs for time series. Prior studies show that LLMs struggle with direct numerical forecasting or zero-shot time-series reasoning when signals are serialized as text \citep{tan2024useful,merrill2024struggle}. A domain module reduces this burden by keeping temporal objects native, exposing operations through typed tools, and using the LLM for planning, context integration, and evidence synthesis.

\subsection{Contextualized and multimodal time series}

Contextualized time series connect numerical signals with external events, documents, images, domain descriptions, and natural-language questions. Existing benchmarks evaluate whether models can use textual context for forecasting, answer temporal questions, reason over multimodal evidence, handle health signals, and solve event-informed tasks \citep{contextiskey2025,timemqa2025,mtbench2025,mmtsbench2026,tsaqa2026,tsrbench2026,hearts2026,temporalbench2026}. These evaluation settings motivate two domain components: temporal grounding of external context, and leakage-aware evaluation of context-conditioned reasoning.

The resulting literature can be read through three connected strands: time-series-only analysis, agentic temporal workflows, and contextualized or multimodal temporal reasoning \citep{timeclaw2026harness}. In a Time Series Agent, these strands correspond to different parts of the \TSHarnessModule{}: contextual methods contribute evidence and retrieval interfaces, TSQA benchmarks~\cite{tsaqa2026} contribute validation tasks, and multimodal temporal methods contribute cross-modal state representations.

\subsection{Agentic systems for temporal workflows}

Representative Time Series Agent work makes temporal reasoning tool-grounded. TS-Agent reasons over raw time series through iterative statistical insight gathering \citep{tsagent2025}. TimeART trains tool-augmented time-series reasoning on TimeToolBench \citep{timeart2026}. TSAG evaluates financial tool selection and faithfulness \citep{tsag2026}. Agentic RAG for TSA routes requests through a hierarchy of task-specialized agents \citep{agenticrag2024}. FETA, ZARA, TESSA, and MarsTSC use multi-agent, retrieval-augmented, annotation, or self-evolving knowledge-bank mechanisms for classification, activity recognition, and annotation \citep{feta2025,zara2025,tessa2024,marstsc2026}. These works primarily contribute to interface design, tool use, role decomposition, and task-specific evidence construction.

Workflow agents place temporal models inside end-to-end analysis procedures. Existing systems decompose forecasting into curation, planning, modeling, validation, reporting, retrieval, explanation, assistant interaction, and last-mile revision \citep{timeseriesscientist2025,timecap2025,timexl2025,flairr2025,nexus2026,moiraiagent2026,timecopilot2026,lastmile2026,alphacast2025,finarena2025}. Similar workflow designs have also been developed for anomaly detection, diagnosis, and domain monitoring \citep{argos2025,anomamind2026,chatad2026,timera2025,sagead2026,dast2026,sagesleep2026}.

Multi-agent systems coordinate heterogeneous evidence or roles. TS-Debate separates numeric, visual, and textual evidence agents, while MAS4TS coordinates Analyzer, Reasoner, and Executor roles for visual time-series reasoning \citep{tsdebate2026,mas4ts2026}. WeatherTGD and AI-Meteorologist show the same pattern in meteorological interpretation, using specialized roles or structured report-generation modules to turn temporal observations into grounded narratives \citep{weathertgd2026,aimeteorologist2025,hierarchicalmeteorologist2025}. These works primarily contribute to multi-agent coordination, but their value depends on a shared temporal evidence state.

\subsection{Adjacent LLM agents for data science}

Time Series Agents also inherit ideas from LLM agents for data science and machine-learning engineering. Prior work shows how agents can write code, inspect intermediate outputs, reuse cases, modify files, run experiments, and reason over machine-learning pipelines \citep{datainterpreter2025,dsagent2024,mlagentbench2024}. These systems are not time-series agents by themselves, but they define \GeneralHarness{} mechanisms--code execution, experiment management, stateful artifacts, and evaluation feedback--that can be specialized by a \GeneralTSHarness{} and then by task-specific temporal modules. In our component map, they mainly inform the general-agent layer, whereas time-series agent systems specialize those mechanisms for temporal data and concrete temporal tasks.

\subsection{Self-evolving and component-explicit systems}

Recent systems make runtime components trainable or self-extending. They formulate forecasting as sequential decision-making, compare execution trajectories using task metrics, distill successful procedures into reusable experience, synthesize task-specific forecasters or corrective features, and formalize realistic tasks through workspaces and validation interfaces \citep{castr12026,timeclaw2026explore,kairosagent2026,metacaster2026,crafter2026,aion2026}. A related task-specific direction trains reasoning policies, evidence-selection policies, or process-verifiable traces for temporal reasoning and forecasting \citep{timer12025,timemaster2025,veritime2026,artist2026,counts2025,streasoner2026,timeomni2026}. TimeOmni-1 is included as a non-self-claimed boundary case at \layerTSK{}: its contribution is a time-series reasoning policy rather than an external tool-using agent runtime, but it is treated consistently with COUNTS and VeriTime.

This direction is especially relevant when the system explicitly designs the \TSHarnessModule{} rather than only a task-specific prompt or workflow. A time-series-native runtime can host series in a task-local workspace, expose executable temporal tools, store episodic multimodal memory, and evolve new tools from verified trajectories, thereby connecting forecasting with contextual reasoning and domain-specific temporal analysis \citep{timeclaw2026harness}.

The July--August 2026 increment broadens the corpus across data curation, forecasting, anomaly analysis, and evaluation. BatteryLake and TopoBrick make temporal data and exogenous-variable handling part of the agent workflow \citep{batterylake2026,topobrick2026}; HydroAgent, CastFSR, ReasonCast, and MetaCaster specialize forecasting orchestration \citep{hydroagent2026,castfsr2026,reasoncast2026,metacaster2026}; TimeRLM, AgenticTwin, and EvoTS-Agent specialize anomaly localization or change-point analysis \citep{timerlm2026,agentictwin2026,evotsagent2026}. TimeSage-EV adds a live, rolling-cutoff cross-task benchmark, while TraceBench provides a controlled task-specific root-cause-attribution benchmark \citep{timesageev2026,tracebench2026}.

\section{Contribution Ledger of Existing Systems}

The maintained ledger joins each work's bibliographic identity and first-public date, claim summary and evidence status, GH/GTS/TSK mechanism profile, Harness components, and multi-label task instantiations. Harness and task are recorded as separate axes: the former locates what the runtime contributes, while the latter records where those mechanisms are instantiated.

The contribution split is most useful when it is auditable at the work level. We therefore maintain a work-by-work ledger and use it as the basis for the tables below, with documented screening criteria and an explicit, auditable classification protocol. \emph{Screening} decides inclusion by domain relevance alone: a work enters the count if its primary object is temporal data and it interacts with that data in an LLM runtime beyond being called as a plain model, or proposes an evaluation protocol for time-series agent behavior. \emph{Classification} then assigns, for the percentage claim, one primary contribution level---\layerGH{} for \GeneralHarness{}, \layerGTS{} for \GeneralTSHarness{}, and \layerTSK{} for \TaskSpecificHarness{}---by where the main contribution enters the runtime. Inclusion, level, and whether a paper calls itself an agent are three independent judgments: inclusion is domain relevance, not agent identity, so benchmarks and non-agent modules are counted when they are in scope. The following inclusion criteria and classification rules guide the organization of the reviewed literature. The purpose of the level assignment is not to reduce a system to one label; it is to expose what the paper is mainly teaching the field to build. We additionally record, as pure metadata, whether a paper explicitly claims an agent, agentic, or multi-agent system (marked \selfclaim{} when it does \emph{not}); this metadata never gates inclusion or level. By contribution type we distinguish only \typeSM{} works, which deliver a runnable system or reusable method, from \typeBench{} works, whose primary deliverable is an evaluation benchmark or testbed. Pure temporal foundation models and adjacent data-science agents are discussed elsewhere, but are not counted in this agent-harness statistic.

In the incrementally screened snapshot through 2026-08-30, the ledger contains 77 works. By contribution type, 68 are \typeSM{} works and 9 are \typeBench{} works. The primary contribution distribution is: \layerGH{} 5/77 = 6.5\%, \layerGTS{} 9/77 = 11.7\%, and \layerTSK{} 63/77 = 81.8\%. The self-claim metadata cuts across this: 10 of the 77 works do not call themselves agents, and all ten fall in the \layerTSK{} layer, where they account for 15.9\% of the layer; the current \layerGH{} and \layerGTS{} primary sets are entirely self-claimed. This concentration is a property of the reviewed snapshot, not an inclusion gate: non-self-claimed methods remain counted and are assigned by runtime locus. These proportions describe this enumerated list and are not estimates of all eligible works by the cutoff. Within the snapshot, substantially more works have task-specific than cross-task temporal support as their primary locus; that distribution does not by itself establish maturity or causal underdevelopment. Figure~\ref{fig:contribution-trend} shows the cumulative composition for the 76 ledger entries with an identifiable public month (the remaining software artifact lacks a datable posting); we read it as an August 2026 snapshot rather than a trend, since 53.9\% of the dated works fall in the most recent six months. The historical v2.3 ledger remains a frozen 54-work coding artifact, so its 47/54 reproducibility probe below is retained as a historical result rather than recomputed over the expanded corpus.

\subsection{Literature selection and classification}

\textbf{Screening.} We separate corpus membership from taxonomy assignment. The literature selection covers work available by August 30, 2026. Relevant search concepts combine time-series tasks, including forecasting and anomaly detection, with LLM agents, tool use, reasoning, and workflow design.
After de-duplication, a work is in scope when temporal data are its primary object and an LLM runtime interacts with those data beyond calling a plain predictive model, or when the work proposes an evaluation protocol for time-series agent behavior. Time-R1 \citep{timer12025}, CALM \citep{calm2025}, and TimeOmni-1 \citep{timeomni2026} are positive non-self-claim boundary examples because each contributes an in-scope temporal runtime or reasoning-policy method. Chronos, TimesFM, and TimeOmni-VL are negative controls because they are models without an agent runtime \citep{ansari2024chronos,das2024timesfm,timeomnivl2026}. Mint-Agent is also excluded from the ledger: it is a finance-native research agent, but its public paper does not make a time-series object or time-series runtime contract load-bearing \citep{mintagent2026}. Data Interpreter and TimeSeriesGym remain excluded as generic data-science or ML-engineering agent settings; text-serialization-only studies are excluded for the same runtime-scope reason. The cutoff is determined by the first public version, and a stable official software artifact is accepted when the work itself is released as software. Companion reports are merged only under an explicit system-family work-unit rule with all locators retained. The corpus was assembled incrementally and contains 77 works with public bibliographic or official software sources. The reported distributions describe this reviewed collection.

Screening, locus, and self-claim are independent judgments. A paper can therefore enter the corpus without calling itself an agent, and an uncertain locus assignment is held as \emph{pending} rather than used to reverse the inclusion decision. No work in the current ledger remains pending.

\textbf{Classification.} Table~\ref{tab:locus-rubric} gives the decision rule supplied to coders. For a system or method, the operative boundary between \layerGTS{} and \layerTSK{} is structural. A mechanism is \layerGTS{} when it requires a temporal object but can instantiate different queries, answer schemas, or output adapters without redesigning its core temporal state, action space, tool semantics, reward, or verifier. A dynamically instantiated query contract is therefore not, by itself, sufficient for \layerTSK{}. The mechanism is \layerTSK{} only when those core elements are structurally tied to a fixed task-family output contract---for example, a forecasting horizon and metric reward, a label space, or an anomaly definition---such that changing task family requires redesign. Demonstration on multiple task families raises confidence but does not itself change the locus.

\subsection{Methodological scope and limitations}

The 77-work collection was assembled incrementally, so its percentages describe the reviewed literature rather than field-wide prevalence. The classifications and component mapping involve author judgment. Model-based checks on an earlier 54-work subset and the 84-cell mapping achieved agreement of 47/54 ($\kappa=0.656$) and 59/84 ($\kappa=0.506$), respectively; these checks did not cover the 23 subsequent additions or involve independent human reviewers. The remaining disagreements concern the boundaries between contribution layers and between direct enforcement and supporting roles. Broader literature coverage and independent expert assessment would strengthen these comparisons. The evaluation tests proposed in Section~6.2 also require empirical validation across tasks.

\section{Evaluation: From Output Metrics to Process Metrics}

Evaluation in this survey follows the same contribution-locus axis used throughout the paper: \GeneralHarness{} (\layerGH{}), \GeneralTSHarness{} (\layerGTS{}), and \TaskSpecificHarness{} (\layerTSK{}). The reason is structural. If a Time Series Agent is scored only by output accuracy---the forecast error, the classification score, the detection F1---then only one of the three layers has actually been measured, and it is not the layer where most agentic contribution is claimed. An agent can produce an accurate number through an unfaithful tool call, a leaked future window, or an unverifiable evidence chain, and an output-only metric will not notice. We therefore organize evaluation as \layerGH{} process metrics, \layerGTS{} cross-task temporal contracts, and \layerTSK{} per-task instantiations, mirroring the ledger of Section~5.

The relation between the layers is the one already established for design: \layerGTS{} provides candidate cross-task design-obligation and contract templates, each with an explicit applicability condition, failure predicate, and candidate validation route, while \layerTSK{} instantiates the applicable templates for forecasting, anomaly detection, classification, or QA. This is a two-level relation, not three parallel bins of metrics.

One category sits deliberately outside this three-layer scheme. Standard model-capability suites---conventional forecasting, classification, and anomaly-detection benchmarks \citep{jiang2024empowering,zhang2024llmts}---measure a temporal \emph{component}, not an agent. In the contribution-locus picture they sit \emph{below} the axis: they are necessary-but-insufficient inputs that an agent calls, compares, and verifies, not a layer of agent evaluation. Counting them as agent metrics would re-collapse the component-versus-agent distinction that Section~4.1 is built to preserve. We therefore treat them as substrate and do not list them among the three agent-evaluation layers.

\subsection{General-Harness evaluation: is it behaving like an agent?}

This layer asks whether the system behaves as a competent agent at all, independent of temporal correctness. The relevant metrics are domain-agnostic agent-process measures: tool-call validity, parameter correctness, plan and trace faithfulness \citep{tsag2026}, multi-turn coherence, latency, cost, regression under component evolution, and human-review burden. These are the dimensions exercised by general agent-process and analytical-skill benchmarks and by the process side of temporal ones \citep{mlagentbench2024,timesagemt2026,timeseriesgym2025,tsskill2026}.

A high \layerGH{} score is useful but not sufficient. It provides evidence about valid tool calls, coherent multi-turn traces, cost, and review burden, but says nothing by itself about whether the temporal reasoning underneath is causally sound. A system can pass every \layerGH{} check and still leak future information or misread a unit. \layerGH{} evaluation assesses domain-agnostic agent-process competence rather than acting as a categorical gate; the temporal checks are in Section~6.2.

\subsection{General Time-Series Harness evaluation: conditional cross-task contract templates}

Among the works and benchmarks reviewed here, cross-task temporal contracts are the least standardized evaluation layer. We treat each design obligation as a candidate cross-task contract template whose applicability, validator, and failure criterion must be declared. Each obligation should be assigned one of three applicability statuses: \emph{applicable}, \emph{not applicable} because its precondition is absent, or \emph{not currently evaluable} because the obligation applies but the available artifact exposes no valid test. The latter two statuses are not passes.

\paragraph{Measurement-status convention.} Relevance to an obligation does not make a cited metric a validated cross-task instrument. We distinguish five evidence statuses: \emph{ED}, an established direct instrument for the stated narrow construct on a declared population; \emph{EA}, an established adjacent or task-specific measure; \emph{FE}, evidence that a failure mode exists without an instrument for the obligation; \emph{AP}, an author-proposed reusable falsification fixture not yet validated across systems; and \emph{OM}, an open measurement problem lacking a shared denominator, threshold, aggregation rule, reference population, or validation record. Status attaches to the exact construct measured, not to an obligation as a whole. Passing an AP fixture means only that the tested implementation was not falsified under that fixture.

Within the reviewed evidence set, none of the six obligations has one ED instrument covering its full cross-task scope. Existing work supplies adjacent or task-specific measures for several slices. ED status is clearest only for the narrower conditional uncertainty-validation sub-contract, where proper scoring rules and calibration or reliability diagnostics apply to declared probabilistic constructs and reference populations. All minimal fixtures in Table~\ref{tab:gts-obligation-protocol} are AP tests. Table~\ref{tab:gts-measurement-status} reports the status boundary explicitly.

The literature supports the following narrower status assignments.

\begin{itemize}
  \item \keyterm{(a) Temporal causality.} The cited work provides EA diagnostics rather than an agent-level cross-task leakage instrument. In LLM-based economic forecasting, Lookahead Propensity (LAP) is $P(\mathrm{up})+P(\mathrm{down})$ from a date-only outcome-recall query; contamination is diagnosed through the forecast--LAP interaction, not by interpreting LAP as the fraction of agent decisions using future information \citep{gao2025lookahead}. Original-versus-anonymized financial-news backtests \citep{glasserman2023lookahead} and membership-inference/cutoff-disagreement filtering \citep{memguardalpha2026} are likewise task-specific contamination diagnostics. We therefore classify future-canary perturbation plus trace/dependency auditing as AP, while its agent-level dependency definition, denominator, and aggregation remain OM.
  \item \keyterm{(b) Numerical fidelity.} The cited papers are FE, not fidelity instruments. Gruver et al. report that GPT-4 can underperform GPT-3 in their serialized forecasting setup partly because of number tokenization \citep{gruver2023llmtime}; number-tokenization direction also changes arithmetic accuracy \citep{tokenizationcounts2024}. Neither study tests whether a runtime preserves values, units, scale, timestamps, or precision end to end. Field-wise comparison and round-trip error under predeclared tolerances are therefore AP, with fixture generation, aggregation, and cross-system validation still OM.
  \item \keyterm{(c) Time-indexed state integrity.} TSQBench evaluates data-quality dimension identification and evidence-grounded quality comparison \citep{tsqbench2026}; this is EA and does not test save/load/merge semantics, provenance, or revision vintage across agent steps. The revised-vintage state fixture is AP. Among the cited instruments, we did not identify one joint audit of persistence, merge semantics, provenance, and as-of revision integrity, so that combined route remains OM.
  \item \keyterm{(d) Temporal operation semantics.} TSAG evaluates financial-query parsing, tool selection, parameter extraction, faithfulness, and hallucination using stubbed outputs \citep{tsag2026}; TimeSeriesGym evaluates ML-engineering agents \citep{timeseriesgym2025}; and TimeClaw provides executable temporal infrastructure \citep{timeclaw2026harness}. TSAG and TimeSeriesGym provide EA measures, while TimeClaw provides executable infrastructure that enables stronger checking. Replaying interval, horizon, frequency, alignment, time-zone, axis, and missing-data behavior against an executable oracle is AP; the cited benchmarks do not supply a shared cross-task suite for that combined construct.
  \item \keyterm{(e) Temporal grounding of context.} Existing benchmarks cover complementary EA slices: CiK tests whether essential text improves forecasts \citep{contextiskey2025}; TemporalBench tests contextual and event-conditioned prediction \citep{temporalbench2026}; MMTS-Bench tests cross-modal semantic alignment \citep{mmtsbench2026}; and Dr-CiK directly measures supporting-evidence retrieval and distractor citation within forecasting \citep{drcik2026}. These measures do not form one estimator of relevance, availability-time validity, provenance, and causal status. The time-shift/distractor fixture is AP and the unified construct remains OM.
  \item \keyterm{(f) Output auditability with conditional uncertainty validation.} Core auditability has EA task-specific checkers and AP rerun/evidence-review fixtures, but no universal scalar is implied. Conditional uncertainty validation has a narrower ED status: interval-score decompositions assess conditional calibration of interval forecasts \citep{intervalscore2025}, while confidence elicitation can be evaluated with calibration and failure-prediction metrics \citep{llmconfidence2023}. A structured HFMD forecasting agent reports rolling-origin CRPS and empirical interval coverage as an EA task-specific application \citep{epidemicagent2026}. These uncertainty instruments do not validate the broader evidence chain.
\end{itemize}

The scope of these six design obligations ends at output verification. Converting a verified analytical output into an accountable downstream action is the next lifecycle stage, not a seventh obligation of the same set; we therefore leave decision quality open and return to it in Section~\ref{sec:open-problems}.

\subsection{Task-specific evaluation: per-task instantiation of applicable obligations}

The \layerTSK{} layer does not add a parallel evaluation axis. It instantiates each applicable \layerGTS{} obligation as a concrete task-level contract; different tasks may require different validators without implying a shared scalar metric:

\begin{itemize}
  \item \emph{Temporal causality} becomes horizon-respecting backtest splits in forecasting, label-window separation in anomaly detection, and context-truncation discipline in QA.
  \item \emph{Output auditability} becomes task-specific checking and evidence validation; when probabilistic semantics are present, conditional uncertainty validation may use coverage or reliability diagnostics and proper scoring rules for probabilistic forecasts, classification confidence, or thresholded alerts.
  \item \emph{Numerical fidelity} stays a representation-faithfulness check distinct from predictive quality. We propose a fixture-level operationalization based on field-wise comparison and representation round-trip error against source values under predeclared, field-specific tolerances; this is not yet a validated cross-task instrument. It instantiates as the precision-sensitive channels each task must preserve---history values, scale, and units fed into forecasting tools; timestamp and threshold precision in anomaly detection; observed values carried through mask-aware imputation operators. It is deliberately \emph{not} the task's predictive error (forecast error, localization error), because an accurate prediction can still be produced through a lossy or mis-scaled representation.
\end{itemize}

Two concerns are genuinely task-specific rather than instantiations of a cross-task contract: deployment and live evaluation. Live and deployment settings test temporal generalization, operational drift, reproducibility, and revision traces under business constraints \citep{lastmile2026,impermanent2026}. They belong to \layerTSK{} because they are tied to a deployed task's operating conditions, not to a property that holds across tasks.

Two observations from Section~5 line up here, and the alignment is worth stating carefully. In the corrected ledger snapshot, the \layerGTS{} layer is both the least standardized to evaluate (Section~6.2) and the sparser of the two \emph{time-series-specific} layers in the ledger's \emph{primary}-contribution count (Section~5, \layerGTS{} 9/77 against \layerTSK{} 63/77; the \layerGH{} layer, at 5/77, is domain-independent general-agent infrastructure and therefore falls outside this time-series-specific comparison). This 81.8\% task-specific share is a distributional description of the reviewed corpus, not evidence about evaluation maturity or causal proof that cross-task infrastructure is underdeveloped. The word \emph{sparse} needs a qualification: it is partly an artifact of the single-primary-locus counting rule, since Table~\ref{tab:agent-ledger} shows that almost every system touches \layerGTS{} as a secondary contribution, and the reviewed literature often reports task-specific proxies or instantiations of the obligations rather than shared cross-task instruments. The honest statement is therefore not that the cross-task layer is unbuilt or unmeasured, but that it has not been raised to a first-class, cross-task \emph{contract}: it is contributed to and measured task by task, not as a layer in its own right under a shared applicability-and-failure protocol. These remain two independent observations---one about evaluation practice, one about contribution distribution---and the ledger statistic does not \emph{prove} anything about evaluation maturity. We offer the shared-root-cause reading---few first-class \layerGTS{} contributions and little standardized cross-task evaluation both following from the same failure to treat the temporal layer as a first-class object---as a conjecture to be tested, not as a conclusion the counts establish.

\subsection{Open problems}\label{sec:open-problems}

\keyterm{Interface standardization.} Current systems use different tool schemas, workspaces, trace formats, and validation contracts. A Model Context Protocol-style interface for temporal tools and workspaces could make Time Series Agents comparable and composable.

\keyterm{Numerical and temporal faithfulness.} LLMs can misread scales, ignore units, hallucinate trends, or reason over future information. Typed temporal tools, unit annotations, chronological guards, and evidence-grounded generation are required.

\keyterm{Context retrieval under distractors.} Dr-CiK shows that retrieving future-relevant context is difficult when irrelevant documents are available. Temporal grounding of retrieved context and distractor-aware retrieval should become first-class benchmark dimensions.

\keyterm{Memory without leakage.} Episodic memory can improve transfer but may contaminate evaluation, encode obsolete regimes, or retrieve superficially similar but temporally irrelevant cases. Temporal memory needs provenance, expiry, family filters, and replayable audits.

\keyterm{Self-evolving components without regression.} Recent systems suggest that tools, prompts, action-selection modules, skills, and memories can evolve \citep{timeclaw2026explore,timeclaw2026harness,aion2026,castr12026,kairosagent2026}. The open challenge is to verify improvement without overfitting to benchmarks or violating temporal constraints.

\keyterm{Decision-centric evaluation.} The scope of the six temporal design obligations ends at output verification; decision-making is the next lifecycle stage and remains deliberately open rather than being relabeled as a seventh obligation. Many applications require inventory decisions, trading policies, grid control, diagnosis escalation, clinical triage, or maintenance scheduling. Time Series Agent benchmarks should therefore evaluate downstream action quality, counterfactual consequences, and accountability, not only predictive error.

\section{Conclusion}

Within the scope of this survey, we analyze LLM-based Time Series Agent systems as an LLM coupled with a \GeneralHarness{} and a \TSHarnessModule{}. The \GeneralHarness{} denotes the domain-agnostic interface, mechanism, and operation substrate. The temporal module specializes that substrate through time-indexed state, temporal operations, context grounding, and validation, and then instantiates these mechanisms under task contracts such as forecasting, anomaly detection, classification, QA, augmentation, synthesis, and decision support. The cross-task mechanisms constitute the \GeneralTSHarness{}; mechanisms whose state, actions, rewards, or verifiers depend on one of these task contracts constitute the \TaskSpecificHarness{}.

This framing absorbs previous model-centric work rather than replacing it. Classical models, deep forecasters, TSFMs, LLM-based time-series models, multimodal temporal models, and statistical procedures can become callable components inside a temporal runtime. An emerging line of work complements standalone predictive models with executable, verifiable, stateful, and adaptive workflows. Our taxonomy connects each work's main contribution to its runtime layer and relates agent components to temporal design requirements and evaluation methods. Using this locus vocabulary, future work can state whether its main contribution improves the \GeneralHarness{}, the \GeneralTSHarness{}, or a \TaskSpecificHarness{} for a concrete time-series task.
